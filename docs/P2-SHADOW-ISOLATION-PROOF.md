**The premise you stated is accepted: a shadow schema in the shared development database is not equivalent to a separate database.** Section 8 lists exactly what it shares and what stops it from interfering; section 9 states the gap that only a separate project closes.

## 1. Schema qualification
**Claim.** Every object the emitted SQL creates, references or grants on lives in `p2s_public`, `p2s_private` or `p2s_auth`; nothing resolves to a live schema, because every function pins `search_path = ''` and every reference is qualified.
**Offline evidence (executed, passing).** P1: after the rewrite **zero** qualifiers of `public`, `private`, `auth` remain in code, strings or comments, and no schema-name literal remains except the PUBLIC role literal in privilege checks. P1b: every **unqualified** name that follows `FROM`, `JOIN`, `UPDATE`, `INTO`, `REFERENCES`, `TRUNCATE`, `ALTER TABLE`, `CREATE TABLE` or `CREATE INDEX ... ON` is in a **reviewed allowance** (catalog tables `pg_*`, set-returning builtins, PL/pgSQL variables `v_*`/`p_*`, records `new`, `old`, `pol`, `r`, subqueries, and the keywords `on`, `then`, `or`, `to`, `set`, `skip` that the files place after those words, plus the PUBLIC pseudo-role and the two test roles in revoke lists). Idempotence: transforming the output again changes nothing. Determinism: two builds give the same bytes. **Negative controls** (each fails exactly the proof it targets while the baseline passes): a query on `public.profiles` (P1 and P4), an unqualified table (`from profiles`, P1b), a schema-name literal left unrewritten (P1).
**RUN-TIME.** The equivalence check: for every function, trigger, constraint, index and policy of the shadow, the same textual rewrite applied to the **live** definition (0001 to 0004, `pg_proc.prosrc` and `pg_get_*def`) or to the 0005 file (not deployed) must equal the shadow definition **byte for byte**; the number of rewrites is asserted; any difference stops the run. A deliberately altered copy must fail the check (control run first).
**Limit.** P1b is a heuristic reviewed by a person (the allowance list above); it is backed by the fact that the same files ran on the real database with `search_path = ''`, where an unqualified table reference would have failed.

## 2. Auth stand-in isolation
**Claim.** The stand-ins touch nothing of the real `auth` schema and read no live data.
**Offline evidence (P2, passing).** The stand-in SQL references only `p2s_*` and `pg_catalog`; its two function bodies contain only `current_setting`, `nullif`, `coalesce`, casts; negative control: a reference to `auth.users` is rejected (P4).
**RUN-TIME.** Before and after: `auth.users`, `auth.identities`, `auth.mfa_factors` digests and counts identical (2, 2, 1 rows today); the real `auth.uid()`/`auth.jwt()` definitions equal the stand-in bodies modulo schema; no object in `auth` created or altered.
**Limit.** The stand-in is an approximation of the real table: Auth's own triggers, constraints and extra columns are not reproduced (section 9).

## 3. Role restrictions
**Claim.** Two roles, both unable to log in or do anything database-wide; their privileges are exactly those the migrations themselves grant (rewritten), on shadow objects only.
**Offline evidence (P3 and P3b, passing).** Exactly two `CREATE ROLE` statements, each `NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION NOINHERIT CONNECTION LIMIT 0`; the only membership grants are those two roles to `current_user` (`WITH INHERIT FALSE, SET TRUE`); **every GRANT and REVOKE in the emitted SQL targets only `p2s_*` objects and only the roles PUBLIC, `p2s_anon`, `p2s_authenticated`** (no database-wide, no all-schemas, no grant option). The 13 explicit grants that result (printed by the tool): usage on `p2s_private` and on `p2s_public`/`p2s_auth` for the test roles; the `select` grants of 0001, 0002 and 0003 (profiles, organizations, billing, members, invites, staff tables, capabilities, audit events); the column-level `update (full_name, phone)` on profiles; execute on the helper functions (`my_org_ids`, `my_owner_org_ids` before 0005 revokes it, `staff_session_ok`, `has_capability`, `my_mfa_owner_org_ids`); execute on the RPCs; execute on the throttle for both roles; execute on the two claim readers. Negative controls: a superuser role, a BYPASSRLS role, a membership grant to another role, a grant to the real `anon`, a grant on a real object: each rejected.
**RUN-TIME: effective-privilege audit.** For each role, using `has_*_privilege` over the catalog, enumerate every schema, table, view, sequence, function and type **outside** the shadow and outside `pg_catalog`/`information_schema` and assert that the role has no privilege except those held through PUBLIC by default (USAGE on the schemas `public` and `extensions`, EXECUTE on `extensions` functions, and for the database CONNECT and TEMP). The exact list is printed. **Anything beyond that list stops the run.** Role attributes are read back from `pg_roles` (`rolsuper`, `rolbypassrls`, `rolcreatedb`, `rolcreaterole`, `rolreplication`, `rolcanlogin`, `rolconnlimit`, `rolinherit`) and compared.
**Limit (stated, not hidden).** Privileges inherited through PUBLIC cannot be removed per role: the roles can resolve names in the live `public` schema (USAGE) but hold **no table, sequence or function privilege** there (the live objects revoke PUBLIC explicitly, and the global default `revoke execute on functions from public` is already in place); the audit above proves this from the catalog rather than assuming it.

## 7. Advisory-lock namespace (a finding from preparing this dossier)
**Problem.** Advisory locks live in a **database-wide** key space. The shadow copies of the staff, window, recovery and refresh functions would otherwise take the **same** keys as the live functions (`m1:last_admin`, `p2:structure_check_refresh`, `p2:owner_window:<id>`, `p2:owner_recovery:<id>`), so a shadow race test could block, or be blocked by, a real operation.
**Control.** A declared rewrite rule namespaces every literal key prefix (`m1:`, `p2:` become `p2s:`...): 8 sites (table above). P8 (offline, passing) asserts that **no** un-namespaced prefix remains and that namespaced sites exist; negative control: an un-namespaced `hashtextextended('m1:last_admin', 0)` is rejected. Per-user keys hash the id of a **shadow** user, which does not exist in the live database. (The prefix `p2:rl:v1:` is a hash input for a counter key, not a lock; it is namespaced too, harmlessly.) The equivalence check applies the same rule to the live definitions, so the proof of identical logic is unaffected.
**RUN-TIME.** Before the first test and during the run, `pg_locks` must show **no advisory lock held by any other session**; the run is scheduled in a declared quiet window (no staff, no organizations exist on the project today).

## 9. What remains different from a separate database (the residual gap, stated)
1. **Same instance**: a runaway test (long locks, heavy I/O) can affect the live project during the run; the live project currently has no traffic beyond validation accounts, and the run is aborted on any anomaly. 2. **Same cluster roles and PUBLIC defaults** (section 3 limit). 3. `service_role` is **not modeled** (its BYPASSRLS and default grants): it is mapped to `p2s_anon` in revoke lists and role-literal checks, so the migrations' "no service_role privilege" self-checks re-check `anon` instead of the real role; that property was observed on the live project by earlier checks and is covered again in the separate-project phase. 4. The stand-in `auth` objects approximate the real ones (section 2 limit). 5. Platform behavior (GoTrue, PostgREST, pooler, Dashboard, event triggers beyond those listed) is not represented. **Therefore the shadow phases can establish the correctness of the logic, but real Auth/PostgREST integration still requires the separate disposable Supabase project (decision D-V4: deferred until the offline and approved shadow phases are complete).**

## 10. Stop conditions (any one ends the run before the next step; no retry, no silent edit)
Hash mismatch of any emitted file or source; the control run of the equivalence check not failing on a deliberately altered copy; any equivalence difference; effective-privilege audit beyond the PUBLIC defaults; role attributes different from the declaration; any other session holding an advisory lock at the start; any difference in the snapshots outside the shadow at any checkpoint; any `pg_default_acl` change; the live `auth.uid()`/`auth.jwt()` definitions differing from the stand-in bodies; the probe (rolled back) failing to create the roles or to `SET ROLE`; cleanup verification failing.

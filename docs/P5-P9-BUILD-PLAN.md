# P5 to P9 build plan (build first, test together, harden in P10)

Mandate of the project owner, 2026-11-11: build everything through P9 (code, SQL, automated tests); then test it automated and manually as one round; the security review and fixes are P10. Nothing is applied to a database, committed, pushed or deployed without the owner's explicit approval (SQL stays under `supabase/review/pN/` until promoted; the pinned apply harness with a rolled-back rehearsal is used, as for P3 and P4). Rules of `ROADMAP.md` still hold: backend and frontend together, no UI-only placeholders, reuse the P1/P2 architecture, server-authoritative money in integer cents, tenant isolation (`organization_id` + RPC membership checks), the public marketing site untouched.

**Apply strategy:** because several migrations will exist at once, a chain rehearsal (all new migrations in order, in ONE rolled-back transaction) is run first, then each migration is committed in order on the owner's approval. Bugs found by the owner's test round are fixed by new migrations (orders, invoices, ledgers are append-only; there is no down step).

## Assumptions (defaults; each is data or a small code change, tell me to change any)
1. **Files:** documents (label artwork, agreements, certificates, payment proofs) live in one private Supabase Storage bucket, path prefix `<organization_id>/`, PDF/PNG/JPG up to 10 MB, registered by RPC, read through short-lived signed URLs created server-side with the user's session.
2. **Setup fee:** $4,000 setup-fee invoice plus a $1,000 prepay funding requirement (the observed USW split without a wallet). Fee schedule and settings are data (P8 screen).
3. **Funding requirement types:** `prepay_invoice`, `deposit_invoice`, `credit_terms`, `waived` (staff + reason). `wallet` stays unavailable (Gate G3).
4. **Compliance gates** G1 to G6 (SECURITY-ASSESSMENT) exist as records; go-live (step 9) and live keys need G1, G2, G4, G5 and G6 recorded; G3 only for the wallet. Staff with `gates.write` record them.
5. **API:** `/api/v1/...` route handlers authenticate with a hashed API key through definer RPCs (anon may execute only those RPCs). Test keys create sandbox orders only; live keys need go-live. Webhooks: HTTPS only, HMAC-SHA256 signature, retry with backoff, an outbox processed by a protected cron route.
6. **Inventory:** one append-only movement ledger, balances written only by the movement RPC, `on_hand >= 0`, `reserved <= on_hand`; customer-owned stock allocatable only to its owner. Fulfillment lifecycle states as observed (pending, queued, allocated, picked, packed, ready, shipped, delivered, cancelled).
7. **Commissions:** plan with a percent rate per organization (default none), 14-day hold from invoice payment, append-only ledger, manual payout records (no payout provider).
8. **Notifications:** an email outbox with templates and preferences; no email provider is wired (a sender adapter and an env switch are prepared). In-app notices where cheap.
9. **Not built:** card/ACH processing, wallet top-up, carrier API integration (tracking is entered by staff), returns portal, two-person approvals, SSO, public sign-up (applications are intake records reviewed by staff).

## Phases and milestones
Each phase ends with: migration draft + static checks, server layer, customer and admin screens, authorization tests for every action, typecheck, lint, tests, build; roadmap and memory updated.

### P5 Fulfillment onboarding
M1 model (step engine, states, dependencies, funding types) and schemas, tests. M2 migration: documents + storage policies, onboarding templates/instances/steps/submissions/reviews/events, private products and SKU mapping, label designs/versions, packaging options/selections, store connection, agreements/signatures, funding requirements, launch reviews, compliance gates; invoices extended for non-order (setup fee) invoices. M3 server layer. M4 customer nine-step setup at `/client/fulfillment/setup`. M5 admin queue, step review (approve or reject with reason and instructions), agreement and funding handling, gates, go-live at `/admin/fulfillment`. M6 tests. Steps 4 and 5 (store connection, sandbox test order) are completed in P6.

### P6 API keys, docs, webhooks, sandbox
M1 key model (prefix, hash, scopes, environment). M2 migration: api_keys, events, idempotency records, webhook endpoints/deliveries/outbox, fulfillment_orders (sandbox first). M3 server layer and `/api/v1` handlers (authenticate, create/get sandbox order, idempotency). M4 customer `/client/api-keys` (create shown once, revoke), webhook endpoints and delivery log, `/client/docs`. M5 admin `/admin/integrations`. M6 wire onboarding steps 4 and 5; tests.

### P7 Inventory and warehouse
M1 ledger and fulfillment-state model. M2 migration: warehouses, locations, lots, movements, balances, reservations, receipts, fulfillment order allocation/pick/pack/ship, shipments with tracking, exceptions. M3 server layer. M4 customer `/client/stock` and fulfillment order views. M5 admin `/admin/inventory` and `/admin/fulfillment` queues (receive, adjust, allocate, pick, pack, ship). M6 tests (including oversell prevention in the model and SQL text).

### P8 Admin operations and management
Organizations (list, detail, create, suspend/reactivate, terms, flags, members, invites), applications (intake, review, approve creates the organization), customers, staff management (create, roles, disable) using the P2 RPCs, settings (payment instructions, fee schedules, numbering, flags view), customer account page (profile, members), admin overview dashboard with finance KPIs.

### P9 Certificates, commissions, notifications, reporting
Certificates (lots and orders, availability, customer `/client/certificates`, admin attach), commissions (plans, referral links, ledger from paid invoices after the hold, payouts; customer `/client/commissions`), notifications (outbox, templates, preferences, sender adapter), reporting (`/admin/reports`: sales, receivables aging, inventory, commissions, CSV export).

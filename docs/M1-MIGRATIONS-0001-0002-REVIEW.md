## 2. Findings and corrections
### F-1 Staff/member mutual exclusion
**Finding (rev1):** the staff-side guard ran only on INSERT, `staff_members.user_id` could be changed by UPDATE, reactivation was unchecked, and no guard demanded a safe isolation level (under REPEATABLE READ the second transaction can miss the first one's commit, leaving both rows).
**Correction (0002):** `guard_staff_not_member` runs `BEFORE INSERT OR UPDATE` on `staff_members`; `user_id` is immutable; every insert/update takes the per-user advisory lock then checks for an active membership (so reactivation is re-checked); the member side keeps `BEFORE INSERT OR UPDATE` with the same lock and checks whenever the resulting membership is active (0001 already makes member `user_id` immutable). Both sides raise unless `transaction_isolation = 'read committed'`. The lock is released at commit, so the later transaction sees the earlier commit.
**Lock hierarchy (documented in the file header):** (1) advisory `m1:last_admin`, (2) organization row, (3) per-user advisory lock. Trigger names sort so `staff_members_last_admin_lock` runs before `staff_members_not_member` and `organization_members_guard` before `organization_members_not_staff`; no path takes them in another order, so no deadlock cycle is introduced (to be demonstrated by test T-EX-8).
**Tests required (all NOT RUN):** T-EX-1 two connections, staff-insert vs member-insert for one user, both orderings: exactly one commits; T-EX-2 staff-reactivation (`disabled`→`active`) vs concurrent membership add; T-EX-3 member `removed`→`active` vs concurrent staff insert; T-EX-4 `staff_members.user_id` update rejected; T-EX-5 UPDATE of a staff row for a user with an active membership rejected; T-EX-6 member insert for an existing staff user (any status) rejected; T-EX-7 both guards raise under REPEATABLE READ and SERIALIZABLE; T-EX-8 a 200-iteration mixed loop of the above produces zero deadlocks (SQLSTATE 40P01 counts as failure) and the invariant "no user is both staff and active member" holds at the end of every iteration.
**Unresolved:** guards require READ COMMITTED, so any future caller that raises isolation will fail rather than skew (acceptable; see D-13). Lock behavior is unproven until T-EX runs.

### F-2 MFA factor authorization binding
**Finding (rev1):** `staff_mfa_factors` had only a plain FK to `staff_members` and a loose `window_id`; nothing in the database tied a factor to a valid window, the window's target user, the window's state, or the factor's real type/status/creation time; the claim logic lived only in a future RPC.
**Correction (0002), enforced by the database rather than by a future RPC:**
- `staff_mfa_enrolment_windows` gets `unique (id, target_user_id)`; `staff_mfa_factors` gets the composite FK `(window_id, user_id) → windows (id, target_user_id)` (a factor's user must be the window's target; `on delete cascade` since rev2.1, see P2-1) and `unique (window_id)` (one approval per window, single use).
- Trigger `guard_staff_mfa_factor_insert` (before insert on `staff_mfa_factors`) locks the window row `FOR UPDATE` and refuses unless, at `clock_timestamp()` (not the transaction start): the window exists, targets this user, is not revoked, not consumed, authorized ≤ now < expiry; the target is an active staff member; and the factor exists in `auth.mfa_factors` for this user, is `verified`, is `totp`, and was created at or after window authorization and not in the future. It then marks the window consumed in the same transaction and stamps `approved_at`. It reads only `id`-matched `user_id`, `status`, `factor_type`, `created_at`; **never the `secret` column**.
- Trigger `guard_enrolment_window_insert` (windows are created open, for an active staff target, by an active admin, or by the owner-run bootstrap with `authorized_by` NULL). Trigger `guard_enrolment_window_update`: identity, target, authorizer, timing and reason are immutable; a revoked window and a consumed window cannot change; nothing is un-revoked or un-consumed. Trigger `guard_staff_mfa_factor_update`: approvals are immutable.
**Atomic claim requirements for migration 0007** (the RPC must, in one transaction): (1) take the user from `auth.uid()` only (never a parameter); (2) require an active staff row and JWT `aal2`; staff session checks that depend on an approved factor must **not** be used for the claim itself; (3) accept only the factor id from the client and locate the caller's own open window (`target_user_id = auth.uid()`, unique open window); never accept a window id from the client; (4) insert into `staff_mfa_factors` and let the trigger validate and consume atomically (the RPC never sets `consumed_at` itself); (5) refuse non-TOTP factors (also enforced by the trigger); (6) write the audit event in the same transaction and return structured denials without raising so the denial audit persists; (7) rate-limit claim attempts per user (needs `private.rate_limits`, so 0007 follows 0006); (8) return generic errors that do not reveal which condition failed to an unauthenticated or wrong user; (9) never select `secret`; the static check is a build gate; (10) first close lapsed windows before authorizing a new one (the one-open-window index counts an expired but unrevoked window as open; see D-8).
**Negative tests required (NOT RUN):** at table level in 0002 (T-FB-1..12): approval for a user other than the window target (composite FK rejects); expired window; window not yet open; revoked window; consumed window; second approval for one window; unknown window; factor id that does not exist; factor of another user; factor not `verified`; factor of type phone or WebAuthn; factor created before the window opened; staff target disabled; window created by a non-admin; window authorizer equals target; update or un-consume of a window; update of an approval. At RPC level in 0007 (T-MFAW-*): the same set through `claim_staff_mfa_factor`, plus unauthorized caller (customer, finance/ops/support, admin at aal1), mismatched window (window for X, factor for Y), and two simultaneous claims (exactly one succeeds).
**Unresolved:** correctness of the trigger (including reading `auth.mfa_factors` as the definer) is unproven until V5b and T-FB run on PostgreSQL.

### F-3 Last-admin (and last-owner) protection
**Finding (rev1):** counts happened in a BEFORE row trigger; a single statement removing several admins/owners could be judged row by row on a possibly stale view, and the design depended on visibility rules of earlier rows in the same command. TRUNCATE bypassed everything. A first rev2 attempt using only an AFTER check would have **missed cascade deletes**, because internal foreign-key cascade actions fire before ordinary AFTER triggers and remove the admin's role rows before the AFTER trigger could recognise an admin (found during this review; corrected).
**Correction:** two-part guards.
- *Owners (0001):* BEFORE row trigger (READ COMMITTED required, identity immutable, organization row `FOR UPDATE`) plus AFTER row trigger `check_last_owner` that counts active owners of the organization at statement end (closed organizations exempt). It depends only on the OLD row, so cascade order does not matter.
- *Admins (0002):* BEFORE row trigger `guard_last_admin_lock` (READ COMMITTED required; if the change can shrink the active-admin set it takes the single advisory lock and sets the transaction-local marker `m1.admin_shrink = '1'` while the admin's role rows are still visible) plus AFTER row trigger `check_last_admin` that, when the marker is set, requires at least one active admin in the final state. The marker can only cause an extra check, never skip one (the BEFORE trigger overwrites it with `'1'`). Covers staff-role demotion/deletion, status disabling, deletion of the staff row, and deletion of the auth user (cascade), including multi-row statements.
- `BEFORE TRUNCATE` triggers block TRUNCATE on `organization_members`, `staff_members`, `staff_roles` (via invoker function `block_truncate`).
**Concurrency tests required (NOT RUN; two or more real connections, 100 iterations each, deadlocks and unexpected SQLSTATEs count as failure):** T-LA-1 two admins, each transaction removes the other's `admin` role: exactly one commits, ≥1 admin remains; T-LA-2 each demotes the other (role change `admin`→`finance`): same; T-LA-3 each disables the other (`status`): same; T-LA-4 two connections delete each other's auth users (cascade): same; T-LA-5 mixed (A deletes B's role while B disables A); T-LA-6 one multi-row statement removing/disabling/deleting all admins fails and changes nothing; T-LA-7 three admins, two concurrent removals: both may succeed, one remains; T-LA-8 removing a disabled admin's role while another active admin exists succeeds and does not trip the guard; T-LA-9 TRUNCATE refused on the three tables; T-LA-10 guards refuse REPEATABLE READ; T-LA-11 owner equivalents of 1–7 (two owners cross-demoting, cross-removing, cascade via auth user deletes, multi-row demotion of all owners, closed-organization exception); T-LA-12 the marker does not leak: after a passing shrink, an unrelated later statement in the same transaction still behaves correctly.
**Unresolved:** **correctness is not claimed.** It rests on READ COMMITTED semantics, trigger firing order and the marker, all to be proven by execution evidence. Assumption U-2 below.

### P2-1 Factor approval deletion semantics
**Observation:** `staff_mfa_factors` blocks UPDATE (`guard_staff_mfa_factor_update`) but has no DELETE trigger. That is intentional, and the reasoning is below.
**Approved-lifecycle proposal (for your approval, D-17):**
1. *Creation* only through `guard_staff_mfa_factor_insert` (validated, consumes the window atomically).
2. *Never updated* (trigger).
3. *No API role can delete* (no privilege). *No M1 RPC deletes.* The functions planned for 0007 are: authorize window (insert), revoke window (update of three columns), check, claim (insert approval), staff role grant/revoke (`staff_roles` only), staff status (update). None deletes approvals or windows. **0007 requirement:** no function may `DELETE FROM` or `UPDATE` `private.staff_mfa_factors`, and none may `DELETE FROM` `private.staff_mfa_enrolment_windows`; the only writes to windows are the insert in authorize and the three-column revoke. Verified by reviewer checklist and test T-LC-3 (source scan of every function in `public` and `private`, re-run on each later migration). The current checker does not scan 0007 because it does not exist, and no rule is added for it now.
4. *Removing a factor happens in Auth* (unenroll or admin API), not by deleting our row. An approval whose Auth factor no longer exists is inert: `mfa_check_ok()` counts approvals only when joined to an existing verified TOTP factor, so an orphan approval grants nothing. Approvals are an append-only history that is cleaned up only by cascade.
5. *Deletion cannot widen access.* Deleting an approval can only turn a factor from approved to unapproved and deny staff. Escalation needs an INSERT, which is fully guarded. So the risk of an unguarded DELETE is availability, not privilege.
6. *FK cascade on staff deletion* (direct delete of `staff_members`, or deletion of the auth user): `staff_roles` cascade; windows cascade through `target_user_id`; factors cascade through `user_id`; a window's deletion also cascades to its factor through the composite FK. Cascade DELETEs run no UPDATE trigger and there is no DELETE trigger on either table, so they pass. The last-admin guard still applies first (deleting the last admin fails).
**Defects found by this analysis (fixed in rev2.1; unproven):**
- *Composite FK without an action (NO ACTION).* In the cascade, the window deletion would be checked immediately after that inner delete, while the approval rows (removed by a separate cascade that sorts later) still existed, so the whole staff deletion could fail. Fix: `on delete cascade` on the composite FK, which makes the result independent of the order of the two cascades.
- *`ON DELETE SET NULL` on `authorized_by` and `revoked_by` is an UPDATE,* which the window update trigger rejected, so deleting any admin who ever authorized or revoked a window would fail. Fix: the trigger now allows these two columns to change **to NULL only**, never to another value.
**Why there is still no DELETE trigger:** a trigger that blocks direct deletes would have to allow cascade deletes. The only discriminator found is "the parent staff row no longer exists", which depends on the parent deletion being visible to the cascade query and on trigger order, neither proven, and a wrong assumption would make staff deletion fail. It would also block legitimate future cleanup. Since deletion only reduces access and no API or RPC path exists, the remaining exposure is owner-level mistakes, which a trigger would not stop (owners can disable triggers, R-2). Optional hardening is recorded as **D-17** and reconsidered after the cascade tests.
**Tests required (NOT RUN):** T-LC-1 deleting a staff member who has an approved factor and windows, by direct DELETE and by deleting the auth user, succeeds and leaves no rows; T-LC-2 deleting an admin auth user who authorized and revoked windows for others succeeds and the windows keep their rows with the authorizer NULL; T-LC-3 source scan: no function other than the guard triggers references `DELETE`/`UPDATE` on the two tables; T-LC-4 deleting an approval at owner level denies staff and never grants; T-LC-5 deleting a window cascades its approval; T-LC-6 the last admin still cannot be deleted by cascade; T-LC-7 an orphan approval (factor removed in Auth) grants nothing.

### P2-2 Factor enrollment policy
**Rule as implemented (unchanged):** an approval requires an `auth.mfa_factors` row that exists, belongs to the window's target, is `verified`, is `totp`, has `created_at >= window.authorized_at` (and not in the future), and is claimed while the window is still open.
**What that means, stated explicitly:** the factor must be a **newly created TOTP factor inside the authorized window**. A factor created before the window was authorized can never be approved; the user must remove it in Auth and enrol again after authorization. First-admin bootstrap order is therefore: open the window, enrol, verify, claim. Existing factors (for example a test factor) are not grandfathered.
**Three different things, kept apart:**
| Concept | Source | Used by the approval trigger? |
|---|---|---|
| Factor **creation time** | `auth.mfa_factors.created_at` compared with the window's `authorized_at` (database clock) | Yes |
| Factor **verification time** (when `status` became `verified`) | not read (`updated_at` is outside the approved column set) | No. Inferred only: it is verified at claim time, created inside the window, and the window is open at claim, so verification happened between creation and claim, inside the window. The exact moment is unknown to the trigger. |
| **Recent TOTP verification of the session** (step-up: JWT `amr` totp timestamp within 60 s, session-bound) | JWT claims | No. Belongs to 0004; a trigger cannot read JWT claims in a way we rely on. |
**Status:** this matches the specification text of §5.12 (`created_at >= window.authorized_at`), so the rule is not changed. **Open decision D-16:** (a) confirm that "newly created inside the window" is the intended policy (no change proposed); (b) decide whether `claim_staff_mfa_factor` must **also** require a fresh TOTP `amr` entry (within 60 s, same session) to show that the claimer has just verified this factor. The specification does not require it and the trigger cannot enforce it, so it would be an RPC requirement for 0007 plus a validation. I recommend requiring it, but it is not assumed.
**Tests required (NOT RUN):** T-FP-1 factor created before the window: rejected; T-FP-2 created at or after authorization and before expiry: accepted; T-FP-3 created after expiry: rejected; T-FP-4 pre-existing verified factor: rejected; T-FP-5 unverified factor: rejected; T-FP-6 verified after the window closed: claim rejected because the window is closed; T-FP-7 factor of another user created inside the window: rejected; T-FP-8 two new factors in one window: the first claim succeeds, the second is rejected (window consumed); T-FP-9 boundary instants (equal to `authorized_at`, equal to `expires_at`).

### P2-3 Enrollment-window transitions
States: **OPEN** (not revoked, not consumed, before expiry), **LAPSED** (not revoked, not consumed, expired), **CONSUMED**, **REVOKED**.
| Transition | Columns written | Database enforcement (rev2.1) | Required of the 0007 RPC |
|---|---|---|---|
| create → OPEN | all | insert trigger: active staff target, active admin authorizer (or NULL for the owner-run bootstrap), created open; CHECKs: ≤ 60 min, not self | `authorize` inserts only; first closes lapsed windows (see LAPSED → REVOKED) |
| OPEN → CONSUMED | `consumed_at` | factor-insert trigger sets it atomically with approval. **The update trigger permits NULL→timestamp from any caller**, because it cannot tell who is writing; the CHECK forbids it together with `revoked_at` | **No RPC may write `consumed_at`.** Consumption happens only through the claim's insert into `staff_mfa_factors` |
| OPEN → REVOKED | `revoked_at`, `revoked_by`, `revoke_reason` | update trigger allows NULL→value on these; CHECK forbids if consumed. **The database does not require `revoked_by` or a reason, nor that the caller is an admin** | `revoke` RPC: caller is an active ADMIN with `staff.manage`, JWT aal2, step-up; locks the window `FOR UPDATE`; refuses if CONSUMED or REVOKED (structured denial); writes exactly these three columns in one UPDATE, `revoked_by = auth.uid()`, non-empty reason; audits in the same transaction |
| LAPSED → REVOKED | same three | same | cleanup by the authorize RPC or a sweeper; `revoked_by` NULL, reason `expired`; audit `expired` |
| LAPSED → CONSUMED | | impossible: the factor trigger requires `now < expires_at` | none |
| CONSUMED → anything, REVOKED → anything | | update trigger freezes `consumed_at` once set and freezes the three revoke columns once `revoked_at` is set (except a change **to NULL** of `revoked_by` by FK SET NULL); CHECK forbids both outcomes | RPC treats these as terminal: refuses every operation and never issues an UPDATE to a terminal row |
| `revoked_by` / `revoke_reason` written while `revoked_at` is NULL | | **not blocked** (known gap) | RPC never writes them except together with `revoked_at`; optional CHECK recorded as D-18 |
| `authorized_by` or `revoked_by` → NULL | | allowed (FK SET NULL on user deletion); never to another value | RPC never writes them after insert |
| any other column (`id`, `target_user_id`, `authorized_at`, `expires_at`, `reason`) | | update trigger raises | RPC never writes them |
| DELETE | | no trigger; reached only by FK cascade (P2-1) | no RPC deletes |
**What must live in the database vs the RPC:** the database guarantees identity immutability, terminal-state freezing, mutual exclusion of the two outcomes, time bounds, and atomic approval-plus-consumption. The RPC must supply authorization (who may revoke), required revoke metadata, the "not terminal" refusal, and the prohibition on direct consumption and on deleting. Optional database hardening for the RPC-only items is D-18 (CHECK that revoke fields appear only together; consumption allowed only when a matching approval row exists, for example via a deferred constraint trigger); it is not added now.
**Atomicity (preserved):** the factor-insert trigger locks the window row `FOR UPDATE`, validates, inserts the approval and marks the window consumed in the same transaction; the claim RPC must not split these steps or consume separately. Revoke and claim both lock the same row, so the later one sees a terminal state and is refused.
**Tests required (NOT RUN):** T-WT-1 direct UPDATE of each immutable column rejected; T-WT-2 clearing `consumed_at` rejected; T-WT-3 changing or clearing `revoked_at`, `revoked_by` (to a non-NULL value) or `revoke_reason` on a revoked window rejected; T-WT-4 setting `consumed_at` on a revoked window rejected by CHECK; T-WT-5 revoking a consumed window rejected; T-WT-6 revoking twice rejected; T-WT-7 revoke through the RPC with an empty reason refused (RPC level; at table level the empty reason is a **documented known gap** until D-18); T-WT-8 revoke versus claim in two connections: exactly one terminal outcome, and a consumed window always has its approval; T-WT-9 reconciliation query: no window has `consumed_at` set without an approval (outside cascade deletions); T-WT-10 at RPC level (0007): revoke by customer, finance/ops/support, admin at aal1, admin without step-up, and non-admin staff are refused and audited; revoke of a terminal window refused; no RPC can consume a window directly (source scan, same as T-LC-3).

### P3-1 D-16: does factor claim require a fresh TOTP step-up?
**Specification (recommended, awaiting your confirmation):** a claim requires **both** (A) the factor-in-window conditions, enforced by the database trigger already drafted (new TOTP factor, verified, belongs to the target, created inside the open window), **and** (B) fresh TOTP step-up evidence for the claimer's session, enforced by the 0007 claim RPC before it inserts the approval.
**What does not count as proof of recent verification:** `aal2` alone (it says only that some TOTP verification happened at some time in the session) and factor `created_at` (it records when the factor row was created, not that anyone proved control of it). V3 also showed `iat` is not usable.
**How the 0007 claim RPC consumes the 0004 step-up evidence (in this order, one transaction, before any write; structured denial plus audit on any failure; fail closed):**
1. Caller is `auth.uid()`; an active `staff_members` row exists (the full `staff_session_ok()` is **not** required here, because the caller has no approved factor yet); JWT `aal = 'aal2'`; `session_id` claim present.
2. A `private.step_ups` row exists for (caller, current `session_id`) with `verified_at >= clock_timestamp() - interval '15 minutes'` (database clock; same rule as every other sensitive operation).
3. That row's **`totp_verified_at`** (the JWT `amr` totp timestamp validated at record time, see DEP-1) is **>= the factor's `created_at` and >= the window's `authorized_at`**. This ties the step-up to a TOTP verification that happened after the new factor existed and inside the window. The factor's `created_at` is read with the same five approved `auth.mfa_factors` columns; `secret` is never read.
4. Only then does the RPC insert into `staff_mfa_factors`; the trigger validates the factor and window conditions and consumes the window atomically.
Missing or unparsable `amr`, missing `totp_verified_at`, missing `session_id`, no step-up row, a stale row, a row from another session, or out-of-order timestamps all refuse the claim with no write.
**What this proves and what it cannot:** it proves a person controlling a TOTP factor of this user verified inside the window, after the new factor was created. It **cannot prove the verification used that specific factor**: the JWT `amr` entries observed in V1–V3 carry only `method` and `timestamp`, no factor id (limitation **L-1**). For a first enrolment the new factor is the only verified one, so the evidence is effectively specific; when replacing a factor while an approved one exists, the evidence may come from the old factor.
**Open dependencies (cannot be verified from the current design):**
- **DEP-1** 0004 must store `totp_verified_at` in `step_ups` besides `verified_at`. This is a design addition: §5.3 and the 0004 requirements do not contain it yet.
- **DEP-2** `record_step_up()` must succeed for an active staff user who has no approved factor yet (otherwise first enrolment cannot be completed). Consequence: step-up rows can exist for users with unapproved factors. This is harmless because every other consumer also requires `staff_session_ok()`; step-up is necessary, never sufficient.
- **DEP-3** L-1: whether Auth can expose a factor id in the token (or an Auth hook can add one) is unknown. `auth.mfa_factors.last_challenged_at` is **not used**: it is outside the approved five-column set and its semantics (challenge creation versus successful verification) are unverified; adopting it needs your decision and a validation.
- **DEP-4** New validation **V6** (planned, not run): enrol a second factor while a first is verified, verify it, and record the resulting `aal` and `amr`. V1 evidence covers a first factor only.
**Status:** D-16(a) newly created TOTP inside the window: **accepted** (matches the specification). D-16(b) fresh TOTP step-up at claim: **specified as required, conditional on DEP-1 to DEP-4, awaiting your confirmation.**
**Tests (RPC level, 0007; cannot be run until 0004 and 0007 exist):** T-CL-1 claim with no step-up row refused; T-CL-2 `aal2` but no step-up row refused; T-CL-3 step-up older than 15 minutes refused; T-CL-4 step-up from another session refused; T-CL-5 `totp_verified_at` before the factor's creation refused; T-CL-6 `totp_verified_at` before the window's authorization refused; T-CL-7 missing or unparsable `amr` or `session_id` refused (fail closed); T-CL-8 `aal1` refused; T-CL-9 factor created inside the window but no fresh TOTP (created-at only) refused; T-CL-10 a denied claim writes the denial audit event and no row; T-CL-11 a step-up row of a user with an unapproved factor does **not** open any other sensitive RPC.

### P3-2 D-17: approval deletion, audit, cascades, future RPCs
**Principle preserved:** deleting an approval cannot grant staff access. With `mfa_check_ok()` requiring *zero* verified-but-unapproved factors and *at least one* approved TOTP factor, deleting an approval can only turn a factor from approved to unapproved. Escalation needs an INSERT, which is fully guarded.
**Audit of approval deletion (requirement, implemented with the audit migration 0003 because the audit log does not exist yet):** AFTER DELETE row triggers on `private.staff_mfa_factors` and `private.staff_mfa_enrolment_windows` call `private.write_audit()` with: event `staff_mfa.approval_removed` / `staff_mfa.window_removed`; the approval or window id and the target user as entity; `cause = 'cascade'` when `pg_trigger_depth() > 1` (the delete ran inside a foreign-key action) and `'direct'` otherwise; actor from `auth.uid()` or `system`; never any secret. A failing audit write aborts the deletion (fail closed). The `pg_trigger_depth()` discriminator is an assumption to test.
**Staff deletion cascades produce explicit events:** yes. In 0003, AFTER DELETE on `staff_members` writes `staff.deleted` (cause `cascade` when the auth user was deleted, otherwise `direct`), and each cascaded approval and window produces its own event as above, so the removal of access evidence is never silent. `ON DELETE SET NULL` actions on `authorized_by` and `revoked_by` write `staff_mfa.window_attribution_cleared` with the **previous** value in the audit diff (the identity would otherwise be lost). The window-creation audit event (0007) must record the authorizer so attribution survives.
**Future RPCs cannot silently delete or rewrite approvals:** (1) the only write to `staff_mfa_factors` by any RPC is the claim insert; (2) no function may `DELETE`/`UPDATE` the approvals or `DELETE` windows (source scan T-LC-3, re-run on every later migration); (3) approvals stay immutable by trigger and DELETE is audited by trigger even at owner level (an owner who disables triggers is outside this control, R-2); (4) no API role holds any privilege on these tables (migration self-check); (5) a future "remove approved factor" operation, if ever wanted, needs its own separately approved audited RPC with step-up, not a generic delete.
**Status:** D-17 **proposed as documented, conditional on the 0003 audit hooks (D-6)**; optional DELETE-blocking hardening remains deferred (see P2-1).
**Tests (NOT RUN; need 0003):** T-AUD-1 staff deletion (direct and via auth user) emits `staff.deleted` and per-row approval and window removal events with `cause = 'cascade'`; T-AUD-2 a direct owner-level DELETE of an approval emits `cause = 'direct'`; T-AUD-3 `ON DELETE SET NULL` emits the attribution-cleared event with the previous value; T-AUD-4 no audit diff contains a token, secret or factor secret; T-AUD-5 a failing audit write aborts the deletion; T-AUD-6 each event is written exactly once; T-AUD-7 the `pg_trigger_depth()` cause discriminator is correct for both cases; T-LC-3 and T-LC-4 as in P2-1, plus T-LC-8 after any sequence of deletions `mfa_check_ok()` never changes from false to true.

### P3-3 Window-update trigger: the SET NULL exception, verified from the source

| Column | What the code permits | What it rejects |
|---|---|---|
| `authorized_by` (line 388) | unchanged (including NULL to NULL); non-NULL to NULL | NULL to non-NULL; non-NULL to a different non-NULL |
| `revoked_by` (line 393, only once `revoked_at` is set) | unchanged; non-NULL to NULL | change to a different non-NULL value |
| `revoke_reason` (line 394) | unchanged only | any change, including to NULL (no FK acts on it) |

**Conclusions:** (1) The exception permits only a non-NULL to NULL transition (or no change) for the two attribution columns. (2) Every other column stays frozen, and a NULL-ing cannot smuggle a change to `id`, `target_user_id`, `authorized_at`, `expires_at` or `reason`, which remain rejected in the same statement. (3) **The trigger cannot tell a foreign-key SET NULL from a direct UPDATE**, so any caller with UPDATE access can blank an attribution column, and can do so in the same statement as a legal revoke or consume. Impact is loss of attribution only, and only to owner-level or buggy-RPC callers (no API role has privileges); the 0007 RPC never writes these columns and attribution survives in the audit log (P3-2). Both are optional hardening under **D-18**, not implemented in this documentation-only pass. (5) No static rule is added: a text pattern cannot verify trigger logic and the guardrail's limits are already stated (P2-4).

### P3-4 Rev2.1 cascade fixes: exact expected PostgreSQL behavior (**all unverified until executed**)
Relevant definitions: composite FK `staff_mfa_factors (window_id, user_id) → windows (id, target_user_id) ON DELETE CASCADE`; `staff_mfa_factors.user_id → staff_members ON DELETE CASCADE`; `windows.target_user_id → staff_members ON DELETE CASCADE`; `windows.authorized_by` and `revoked_by → auth.users ON DELETE SET NULL`; `staff_roles → staff_members ON DELETE CASCADE`; `staff_members → auth.users ON DELETE CASCADE`; `created_by`/`granted_by` `ON DELETE SET NULL`. Delete of a staff member, directly or through the auth user, proceeds as follows.
**Scenario A: staff deletion with approved factors.** Precondition: staff user U with roles, a consumed window W1 with approval F1, and a revoked window W0.
1. BEFORE DELETE on `staff_members`: `staff_members_last_admin_lock` asserts READ COMMITTED; if U is an active admin it takes the advisory lock and sets the marker. (`staff_members_not_member` is INSERT/UPDATE only.)
2. The `staff_members` row is deleted.
3. AFTER triggers: the foreign-key cascade actions run as separate inner DELETEs (expected to fire before our lower-case AFTER trigger; assumption U-2):
   a. `staff_roles` rows are deleted; their BEFORE trigger finds U's staff row gone, so it does not set the marker; the AFTER check reads the marker set in step 1.
   b. windows with `target_user_id = U` are deleted (no delete trigger); each window's deletion cascades to its approval through the composite FK, so F1 is removed here (this is the rev2.1 fix; before it, the NO ACTION check could abort the statement while F1 still existed).
   c. approvals with `user_id = U` are deleted (nothing left or the remainder).
   d. `staff_members_last_admin_check` (AFTER row): if the marker is set, count active admins in the final state; zero raises SQLSTATE 23514 and the **whole** transaction rolls back.
4. **Expected outcome:** if U is not an admin, or another active admin exists, deletion succeeds and U's roles, windows and approvals are all gone with no error; if U is the last active admin, deletion fails and **nothing** is deleted (staff row, roles, windows and approvals all remain).
Cases: A1 non-admin staff, direct DELETE: succeeds. A2 same through deleting the auth user: succeeds. A3 last active admin through either path: fails, all rows remain. A4 admin deleted while another active admin exists: succeeds. A5 a window deleted directly at owner level: its approval is cascade-deleted and that staff user is then denied (no approval, factor unapproved). Tests **T-CS-A1..A5** (these refine T-LC-1, T-LC-5 and T-LC-6).
**Scenario B: admin deletion with authorized or revoked windows.** Precondition: admin A (another active admin exists) authorized window W (target X, consumed, with an approval) and revoked window W' (target Y); A also created staff rows and granted roles.
1. Deleting A's auth user cascades to A's own staff row exactly as in Scenario A.
2. `ON DELETE SET NULL` actions run as inner UPDATEs: `windows SET authorized_by = NULL WHERE authorized_by = A`, `windows SET revoked_by = NULL WHERE revoked_by = A`, `staff_members SET created_by = NULL`, `staff_roles SET granted_by = NULL` (and invite columns in 0001).
3. For the two window updates, `staff_mfa_windows_guard_update` runs: the attribution column changes from non-NULL to NULL, which is permitted, and every other column is unchanged, so no error. For the `staff_members` and `staff_roles` updates the BEFORE triggers run (READ COMMITTED assertion; per-user lock and membership check; no admin shrink) and the AFTER admin check runs only if the marker is set.
4. **Expected outcome:** the deletion succeeds; W and W' keep their rows; `authorized_by` of W and `revoked_by` of W' are NULL; `revoked_at`, `revoke_reason`, `consumed_at`, W's approval and X's and Y's access are unchanged; the `created_by` and `granted_by` values become NULL without error. If A is the only active admin, the deletion fails and nothing changes.
5. **Isolation:** the `staff_members` triggers assert READ COMMITTED on every UPDATE, including these NULL-ing updates, so deleting an auth user through a connection at a higher isolation level is expected to fail closed with SQLSTATE 25000. The isolation used by the Auth service when it deletes users is not known (U-5, new test T-ISO-3).
Cases: B1 as above: succeeds with attribution NULLed. B2 `created_by` and `granted_by` NULL-ing: no trigger error. B3 same deletion at REPEATABLE READ: fails closed 25000. B4 A is the only active admin: fails, nothing changes. Tests **T-CS-B1..B4** (these refine T-LC-2 and T-SN-1).
**Label:** every outcome in this section is **unverified** until executed against PostgreSQL.

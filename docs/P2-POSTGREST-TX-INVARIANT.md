# The transaction-end invariant (rev5, F1): what PostgreSQL guarantees, what the API layer must guarantee, and what is NOT yet verified

Status 2026-11-10. **Design and verification plan only. Nothing here was executed or tested.** Written offline; no database, no Supabase project and no environment file was touched.
Sources consulted by web search (public documentation, not project data): PostgREST "Prefer Header" reference (https://docs.postgrest.org/en/stable/references/api/preferences.html) and the Supabase JavaScript reference page for the `rollback()` modifier (https://supabase.com/docs/reference/javascript/using-modifiers-rollback). I did not find the literal list of `db-tx-end` values on the pages the search returned; the value names below are marked accordingly.

## 1. What PostgreSQL guarantees (and what this means for every table in 0003 to 0005)
A row written by a transaction, an advisory transaction lock taken by it and a rate-limit counter incremented by it all belong to that transaction. If it ends in ROLLBACK (explicitly, by an error, or because the client or the API layer decides so), the rows are invisible to every other session and the locks are released. A persistent table, a row lock or an advisory lock does **not** change this. Sequences are the only common non-transactional state and nothing here uses one for accounting. SQL inside a single transaction has no autonomous-transaction feature (the only emulation is a loopback `dblink` connection, which rev5 deliberately does **not** introduce).
Consequence for quotas: the 0005 quotas (5 initiations per operator per 24 hours, 2 per target owner per 7 days) apply to **committed** requests. A rolled-back call consumes nothing and leaves **no audit row either**. Rev4 said "not bypassable by transaction rollback"; that was wrong and is corrected in rev5.

## 2. The invariant that P1 relies on (UNVERIFIED)
> **INV-TX:** for a request to a `public.rpc_*` endpoint of the Data API, the transaction ends with COMMIT when the function returns normally, and with ROLLBACK only when the function raises. No client (browser, script, or the Supabase client library) can make the API layer roll back a call that returned normally.

If INV-TX holds, a refusal that the function *returns* (and audits, as `private.staff_gate` and every refusal in 0004/0005 do on purpose) is committed together with its audit row, and quota rows, rate-limit counters and nonces behave as designed. If INV-TX does not hold, a caller can make any call and discard its trace.
**What would be lost if INV-TX were false (a rolled-back call has no effect, so this is about information and trace, not about unaudited state change):**
- every returned refusal and its audit row (staff denials in `private.staff_gate`, the 12 `'denied'` literals in 0004 and the denial audits of 0005): an operator could probe owner states (`first_enrolment_applies`, `request_pending`, `recovery_locked`, `target_not_eligible`) without any trace;
- every audited READ (for example `rpc_staff_owner_mfa_overview` audits the disclosure of security state): a read could be performed unaudited;
- every throttle counter that is incremented in the same transaction: `rate_limit_hit` for `recovery_code` (5 per 15 minutes) and `mfa_recovery` (3 per hour) in `rpc_owner_recovery_request`, and the per-email and per-address buckets of `rpc_throttle_password_recovery`: guessing recovery codes would not be counted;
- the replay protection `private.consume_nonce`: its row is erased with the transaction. It is safe only while the consumption and the effect it protects are in the same transaction and nothing outside the database acts on the result before commit (rule for every future caller).
What would NOT be lost: a successful mutation always carries its own effect rows and audit row in one transaction; rolling it back removes the mutation as well. A recovery code that only creates a request (24 hour cool-off, owner notified) never grants privileges, so even uncounted guessing yields at most a cancellable request.

## 3. What controls the behavior in PostgREST (documented), and what is unknown here
- The preference header `Prefer: tx=commit` or `Prefer: tx=rollback` exists in PostgREST for testing. Per the documentation it is **not enabled by default**; it is activated by the configuration parameter **`db-tx-end`**. Unless that parameter is set to roll back always, or to honor `Prefer: tx=rollback` per request, the transaction commits when the call succeeds.
- Values: as I recall the reference, `commit` (default), `commit-allow-override`, `rollback` and `rollback-allow-override`. **UNVERIFIED wording:** the pages the search returned do not list these literally, and an older test specification used a different pair of option names, so names have changed between versions. Check the configuration reference of the PostgREST version that serves this project.
- PostgREST can also load settings from the database (`db-config`, role settings of the authenticator role named `pgrst.*`). Which source wins over which, and whether the hosted platform allows a project to change `db-tx-end` at all, is **unknown to me**.
- The Supabase JavaScript client offers a `rollback()` modifier (it sends `Prefer: tx=rollback`). Its existence says nothing about whether the hosted PostgREST honors it.
- **Endpoints in scope:** every `POST /rest/v1/rpc/<name>` of the public schema (16 functions in rev5, the staff RPCs of 0004, `rpc_my_staff_context`, `rpc_throttle_password_recovery` which is callable by `anon`) and, for STABLE functions, `GET /rest/v1/rpc/<name>`. Table endpoints are not used (no DML grant to any API role). The GraphQL endpoint (pg_graphql), if enabled for the project, has its own transaction handling and is **not analysed**; it must be checked separately or disabled.
- **Not tested before:** a search of this repository found no test, script or document that sends `tx=rollback` or reads `Preference-Applied`. The earlier PostgREST tests (48 of 48) covered grants and response shapes only.

## 4. P1 as a claim, and when it may be called proven
**P1 = "the project's Data API satisfies INV-TX".** It is **not proven** and this revision does not claim it. It becomes proven only when the disposable-project test below has been run, with the observations recorded, on the PostgREST version and configuration that production will use, and re-run after any platform or configuration change.
Verification plan (needs a separate approval, a **disposable** Supabase project, fixtures only there, never the shared development project):
1. Record the PostgREST version (response headers of the root endpoint) and the configuration source for `db-tx-end` (platform setting, environment, or `pgrst.*` role settings of the authenticator role in the disposable project).
2. With a fixture staff account holding the capability, call `rpc_staff_owner_mfa_overview` with `Prefer: tx=rollback`. **Pass:** the response has no `Preference-Applied: tx=rollback` header and the audit row exists afterwards. **Fail (INV-TX false):** the header is echoed or the audit row is missing.
3. As `anon`, call `rpc_throttle_password_recovery` twice with the same email hash and `Prefer: tx=rollback`. **Pass:** the second answer is `allowed: false` (the first call committed). **Fail:** both are allowed.
4. Repeat steps 2 and 3 with `Prefer: tx=commit`, with a malformed preference, with `return=minimal`, and with a function that raises (the raise must roll back and leave no audit row, as designed).
5. Confirm no `db-pre-request` function alters transaction handling, and check the GraphQL endpoint (disabled, or the same result).
6. Verify READ COMMITTED: the recovery RPCs refuse REPEATABLE READ and SERIALIZABLE with 25000 (this needs a direct SQL connection in the disposable project, not PostgREST).
**If INV-TX fails:** options in order of preference: (a) disable the override at the platform level if that is possible; (b) block the header at the edge (a proxy or the application server that is the only caller; the public anon key then cannot reach PostgREST directly for these RPCs); (c) move the affected throttles to the application layer as authoritative (the P3 module, with a shared store), accepting that a database-only quota cannot be guaranteed; (d) a separately approved design with a loopback `dblink` autonomous transaction (an extension, credentials and failure-mode cost; **not** part of rev5).

## 5. Why this does not weaken the other guarantees
The MFA, two-person, cool-off and authorization rules are enforced by the data (constraints, triggers) inside the same transaction as the change they protect; a rollback removes both. INV-TX concerns only accounting, audit trace and information leakage, which is why P3 (see `docs/P2-APP-THROTTLE-INTERFACE.md`) adds an application-level attempt counter in a store that is outside the database transaction.

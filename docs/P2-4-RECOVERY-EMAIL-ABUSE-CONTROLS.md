# Password-recovery email: abuse implications and application-level controls

Status 2026-11-10. **Design and analysis only. No email was sent, no email provider was configured, and nothing here has been observed with a real mailer.** The database throttle (0005 rev3, still a draft) can only decide *whether* the application may send; it cannot prove that a send happens, that the link works, or that the response is generic. Those are application obligations, listed below with the tests that must exist before the recovery form is exposed.

## 1. What the 10-minute cool-down does and does not do
Seed: `password_recovery` = 1 allowed request per 600 s window, then a 600 s block that is started by the **second** attempt in the window and never extended by further attempts.
| Property | Result (derived from the `rate_limit_hit` arithmetic) |
|---|---|
| A third party who only knows the email can lock the owner out | **No.** Every allowed request sends a link to the address on file, valid at least 60 minutes. Whoever takes the slot causes the owner to receive a usable link |
| Longest time the owner's own request can be denied | about **20 minutes** after a send (an attacker's second attempt at 599 s blocks until 1199 s); a link from the first send, valid 60 minutes, is in the inbox throughout |
| Highest rate at which an attacker can make emails reach a victim | **one every 10 minutes: 6 per hour, 144 per day** (attempts at 0 s, 601 s, 1202 s, ...; each is allowed because the window has restarted) |
| Enumeration | none from the throttle: it never looks an account up; known and unknown emails are counted identically and every response has the same two-field shape |
**Implication.** The cool-down removes the lockout risk and creates (or leaves open) an **inbox-flooding** risk bounded at 144 emails per day per victim. It also leaves two **project-wide** risks that are not about one victim: exhausting the mail provider's quota, and degrading the sender reputation of the project's domain (complaints and spam folders for all customers).

## 2. Threats
| # | Threat | Who is hurt | Bounded by |
|---|---|---|---|
| T1 | Flooding one victim's inbox with real reset emails | the victim (annoyance, phishing cover: a flood hides a genuine attack email) | 6 per hour per email; 20 requests per hour per client address (blocking, the attacker's own address) |
| T2 | Distributed flooding of **many** victims from many addresses | all victims; the domain's reputation | not bounded per campaign by the database design |
| T3 | Exhausting the provider's hourly or daily send quota | **every user** whose reset email is then refused or delayed (a service-wide lockout of recovery) | provider limits (values for this project **not verified**: check the Supabase Auth rate-limit page and the SMTP provider's plan) |
| T4 | The provider silently refuses a send that the throttle counted as allowed | the owner (waits up to about 20 minutes with no link) | nothing today (see 3.5) |
| T5 | A bot enumerating accounts by response difference or timing | everyone | the generic-response contract (section 3.3) |
| T6 | Mail-bombing through other emails the platform sends (verification, invitations) | victims | out of scope here; same controls apply to those flows when built |

## 3. Application-level controls required (none exists yet; the recovery flow is not built)
**3.1 Bot resistance before the throttle.** A CAPTCHA or proof-of-work challenge (for example a privacy-respecting challenge widget) on the request form, verified **server-side** before the throttle is consulted. This is the main control against T2 and T3 because the database throttle is per email and per address only. Fail closed: no valid challenge means no send and the generic response.
**3.2 Coalescing instead of blocking.** Before sending, check whether an **unexpired, unused** reset link already exists for the account that was sent less than 60 minutes ago; if so, send nothing (the owner has a working link). This keeps the owner safe (the existing link is valid) and cuts the attacker's rate from 6 per hour to about 1 per hour, i.e. at most about 24 per day. **Do not** solve flooding with a long block (for example 24 hours): a block longer than the link lifetime recreates the lockout the non-blocking design exists to avoid.
**3.3 Generic responses.** Allowed, denied, unknown email, challenge failure and provider failure all return the **same HTTP status, body and timing class** ("if an account exists, a message has been sent"). Do the work (hash computation, throttle call, lookup) in a fixed order and pad to a minimum response time so that timing does not reveal the branch. Never reveal the retry-after value to the caller of the public form.
**3.4 Where the link goes.** The email is sent only to the address on file for the account (the identity provider does this when the request is made through its recovery endpoint; never build a path that sends to a submitted address). Link lifetime at least 60 minutes (configure and verify the provider's recovery token lifetime; the default of one hour is the minimum acceptable), single use, never logged, not placed in any query string that is logged by an intermediary beyond what the provider itself does.
**3.5 Provider failure handling (open design point).** If the provider refuses or errors, the throttle has already counted the attempt. Options: (a) accept: the owner waits at most about 20 minutes (simple, but the owner has no link meanwhile); (b) a **release** function for the cool-down callable only from the server after a confirmed provider failure (needs a new server-only database function and a deliberate decision: it must not be callable by the anonymous role, or an attacker could clear their own counter); (c) send first, count afterwards (rejected: concurrent requests would bypass the limit). Recommendation: (a) for milestone 1 with monitoring, (b) only if provider failures are observed in practice.
**3.6 Global send budget and monitoring.** A server-side counter of reset emails per hour for the whole project with an alert at a fraction of the provider's quota, plus a per-domain complaint/bounce feed from the provider. A global hard stop is **not** recommended (it would be an easy denial of service); alert and react (tighten challenge difficulty) instead.
**3.7 Provider-side limits.** Use the identity provider's own per-user minimum interval and project-wide quotas as an additional backstop, with a dedicated sending domain and SPF/DKIM/DMARC configured so that abuse does not damage the main domain's reputation. Verify the actual configured values in the dashboard: this document does **not** assert them.
**3.8 Victim-facing hygiene.** Reset emails carry a short generic notice ("you did not request this? no action is needed; your account is safe") and no content that makes a flood useful for phishing; never include the client address or other request details in the email.

## 4. What the database dry execution can and cannot prove about this
The rolled-back execution of 0005 can show that the seed has the intended numbers, that the cool-down arithmetic behaves as described (first allowed, second and third denied with a retry hint), that the anon function returns the same shape for different inputs, and that no account lookup exists in the function. It **cannot** show: that the application sends exactly one email to the address on file for each allowed request, that the link is valid and usable, that denied requests send nothing, that responses and timing are identical, that the provider did not refuse the send, or that any of the controls in section 3 exist. **Those require application code and integration tests that do not exist yet**, with a fake mailer in tests and no real emails.

## 5. Tests to write with the recovery form (P2.3/P2.4 application work)
Fake mailer: an allowed request produces exactly one send to the address on file, never to a submitted address, with a link lifetime of at least 60 minutes; a denied request produces zero sends; known, unknown, denied, challenge-failed and provider-failed requests return byte-identical bodies and the same status, and their timings differ by less than a threshold; coalescing suppresses a second send while a fresh unused link exists and allows one after 60 minutes; the global budget alert fires; the challenge is verified server-side and fails closed. Cool-down boundary 599, 600, 601 s under concurrency on the database side is covered by the isolated concurrency suite (scenario R5).

## 3. Function by function (new and changed in rev3; unchanged functions: section 8 of the rev2 review still applies)
**`owner_factor_state(uuid)`.** Classifies a user: `unapproved_factor_present` (any verified factor without approval; wins), `approved` (a live approved verified TOTP), `recovery_required` (approval history, nothing live, no unapproved verified factor, so zero verified factors), `none` (no history), `unknown` (any error; every caller denies). Read-only. Unreachable by API roles.
**`rl_user_key(text)`.** `sha256('p2:rl:v1:' || purpose || ':' || auth.uid())`, invoker, reads only the caller's JWT. A caller cannot choose or influence another user's counter. No pepper is needed for user-scoped buckets (the counters are unreachable by API roles).
**`guard_owner_mfa_window_insert` (BEFORE INSERT on windows).** Requires an active organization owner; `first` only in state `none`; `additional` only in state `approved`; `recovery` only in state `recovery_required` **and** a pending request with `cooloff_until <= now < expires_at`; for `first` and `recovery` the authorizer must be an **active staff member holding `owner.mfa.authorize`** at that instant (joined through roles); the window must be created open. Any direct insert by other code meets this trigger.
**`guard_owner_mfa_factor_insert` (approval gate).** As rev2 (window locked `FOR UPDATE`, same user, not revoked or consumed, inside `[opened_at, expires_at)`, active owner, `first` only without history, at most 3 approved, factor exists for this user, **verified**, **TOTP**, **created at or after the window opened**) plus rev3: for `first` and `recovery` windows **no other verified factor may exist** (a leftover cannot ride along). The window is consumed in the same step. Behavior matrix: section 5.
**`owner_mfa_ok()`, `my_mfa_owner_org_ids()`.** Unchanged (fail closed; any verified unapproved factor denies). They do not read any recovery table.
**`rpc_staff_authorize_owner_mfa_window(uuid,text,integer default 30)`.** Gate: `staff_gate('owner.mfa.authorize', ..., step_up = true)` returns `forbidden` (audited) or `step_up_required` (audited) or raises 42501 without a verified staff session (not audited, no flooding). Then: invalid arguments raise 22023 (reason 1 to 200 characters, 5 to 60 minutes); self refused (audited); target must be an active owner else `target_not_eligible` (audited); under a per-target advisory lock the state decides: `none` gives a `first` window; `recovery_required` needs a pending request, an elapsed cool-off and no expiry (`recovery_not_ready`, `recovery_cooling_off`, `recovery_request_expired`, each audited) and gives a `recovery` window; `approved` gives `already_enrolled`; `unapproved_factor_present` tells the operator to remove the leftover by hand first. Lapsed open windows are revoked first, the new window is inserted inside a sub-block that maps the trigger's rejection to `target_not_eligible`. Success is audited with kind, window id and minutes. Single use and boundedness come from the table, not from this function.
**`rpc_staff_owner_mfa_overview(uuid)`.** Same gate and capability, no step-up (read-only), **audited** because it discloses security state: factor state, number of verified factors, pending request with timestamps.
**`rpc_owner_open_factor_window()`.** Only for state `approved` with `owner_mfa_ok()` and `step_up_ok()`; creates an `additional` window authorized by the owner; every other state is **denied and audited** with a code telling the application which operator step is required. A non-owner gets `not_an_owner` (not audited).
**`rpc_owner_claim_factor(uuid)`.** Needs an active owner, `step_up_ok()` and an open window of the caller; the trigger does the eligibility work; its message is never returned (`factor_not_eligible`); a recovery window additionally completes the recovery request and voids the remaining codes (a new set is issued afterwards from the approved session). Audited.
**`rpc_owner_set_recovery_codes(bytea[])`.** Non-owners and staff get `not_available`; exactly ten distinct 32-byte non-null hashes else 22023; needs `owner_mfa_ok()` and a fresh step-up (`step_up_required` audited); under a per-user advisory lock the previous unused codes are voided and the ten rows inserted; a reused hash maps to `code_reused`. The database never sees a code.
**`rpc_owner_recovery_request(bytea)`.** Callable with a password-only (aal1) session. Order matters: (1) validate the hash length; (2) **throttle first** (`recovery_code`: 5 per 15 minutes, then 15 minutes blocked, key from `rl_user_key`), returning `throttled` without further work or audit (so floods cannot fill the audit log); (3) non-owner or staff: the **same generic** `request_not_accepted`; (4) under the advisory lock: lapse stale requests; a cancellation in the last 24 hours gives `recovery_locked`; an existing pending request gives `request_pending` (the code is **not** consumed); (5) look the code up `FOR UPDATE`: a wrong or used or voided code gives `request_not_accepted` (audited as denied; bounded by the throttle); (6) `mfa_recovery` throttle (3 per hour) **before** consuming; (7) consume the code, insert the request with `cooloff_until = now + 24 h`, clear the failure counter, audit. It creates no session, changes no assurance level and approves nothing.
**`rpc_owner_recovery_cancel()`.** The owner cancels their own pending request; a cancellation locks new requests for 24 hours; audited.
**`rpc_my_owner_context(uuid)`.** Own state only; adds `recovery_status` (`none`, `cooling_off`, `ready`, `locked`) and `recovery_codes_remaining`; no information about other users.
**`rpc_throttle_password_recovery(bytea,bytea)`.** Unchanged code; behavior changes through the seed (section 6).

## 6. Per-email throttle: non-blocking design (requirement 10)
**Threat.** The application computes the per-email key for any submitted address, so a third party who only knows an email can burn the victim's per-email quota. Under rev2 that blocked the victim's recovery for an hour.
**Design.** The per-email bucket is a **cool-down**: `max_attempts = 1`, `window_secs = 600`, `block_secs = 600`. An allowed request is the first in a window; later requests in the window are denied silently and nothing is sent; a denial never extends the block (already true of `rate_limit_hit`). **The application contract that makes it safe:** (1) every allowed request sends a genuine reset email to the **address on file** (never to the submitted address) with a link valid for **at least 60 minutes**; (2) a denied request returns the **same generic response and the same timing class** as an allowed one; (3) responses never depend on whether the email exists (the function never looks an account up; unknown and known emails are counted identically).
**Why a third party cannot lock the owner out merely by knowing the email.** Whoever occupies the slot, including the attacker, causes the owner's inbox to receive a usable link. Worst cases (arithmetic of `rate_limit_hit`, corrected 2026-11-10): the owner's own request can be denied for up to about 20 minutes after a send (an attacker's second attempt at 599 s starts a 600 s block), while a link valid for 60 minutes is already in the inbox; and **an attacker who times requests at 0 s, 601 s, 1202 s and so on obtains an allowed request, and therefore an email to the victim, every 10 minutes: up to 6 per hour and 144 per day**. The attacker gains nothing (the link goes to the owner) and the owner cannot be locked out, but the inbox can be flooded at that rate: see `docs/P2-4-RECOVERY-EMAIL-ABUSE-CONTROLS.md` for the implications and the application-level controls this requires.
**Per-address bucket** remains a blocking quota (20 per hour): it only ever blocks the sender's own address and does not depend on knowing an email. A shared address (an office) can exhaust it for its users; the quota is generous for that reason.
**Remaining risks.** If email delivery is delayed or the mailbox is unavailable, the owner cannot recover regardless of throttling (inherent). Link validity below about 30 minutes would reintroduce a gap (denial for up to 20 minutes plus delivery time); 60 minutes is the contract. **Email flooding of a victim (up to 144 per day) is NOT prevented by the database design**; the application controls in the abuse document are required before the recovery form is exposed.

## 7. Rate-limit atomicity, replay prevention, cleanup (unchanged code, unchanged analysis)
Atomicity: one `INSERT ... ON CONFLICT (bucket, key_hash) DO UPDATE` per attempt, the row lock serializes concurrent attempts, window restart and block decisions are inside that statement. Replay: `consume_nonce` is true exactly once until expiry; TTL must be at least the credential lifetime; consumption commits or rolls back with the caller's transaction. Cleanup: at most 50 stale rows per call (`FOR UPDATE SKIP LOCKED`, idle more than 2 days and not blocked); at most 50 expired nonces per call; steady-state growth bounded by the 2-day idle window; the anon throttle can add rows with random keys (about 100 bytes each; monitor table size). **Concurrency behavior is not observed**: `rate-limit-concurrency-isolated.mjs` (R1 to R6, N1 to N5) exists and is gated; see `docs/P2-CONCURRENCY-TEST-PLAN.md`.

## 8. Operator-assisted recovery (end to end, as the SQL supports it)
1. Owner (password session) submits one code: `request_created`, cool-off 24 h, email sent by the application. 2. Owner may cancel (locks 24 h). 3. After the cool-off the **operator verifies identity out of band**, reads the overview, removes **all** factors **by hand** in the dashboard (no code does this), then calls the authorize RPC: state must be `recovery_required` (zero verified factors) and the request ready. 4. Owner enrols a new factor **after** the window opened, verifies it and claims it; the trigger requires it to be the only verified factor; the request completes and old codes are voided; the owner then issues a new set of ten from the approved session.
**Not enforced by SQL:** that the operator really verified identity out of band, and that the removal in step 3 was done correctly. The SQL guarantees the preconditions and leaves an audit trail.

## 11. Dry execution of 2026-11-10: it FAILED inside the transaction (a defect in the draft), and nothing persisted
**Executed once** against `99purity-portal-dev` with the approved hash `c6400e50…0a63` verified, one transaction, rollback guaranteed, no migration history row, no pepper, no Auth user, staff, organization, window or recovery code. **Result: 0005 rev3 raised `"array_agg" is an aggregate function` (SQLSTATE 42809) and the transaction was rolled back.** Pre-checks passed (hash, LF only, no transaction-control text outside function bodies, no `supabase_migrations` reference, project reference, CA pin, strict TLS, history exactly the four applied versions, none of the 0005 objects present). **After the rollback, a fresh connection compared against the snapshot taken before: functions, relations, columns, constraints, policies, triggers, row counts, row digests (capabilities, role capabilities, platform validations, staff, organizations, members), schema and default ACLs, schema list, Auth users, identities and factors, and migration history were all identical** (14 of 14). The failed attempt left no trace.
**Cause (a real defect of the migration's own final self-check, found only by executing it).** `pg_get_functiondef()` raises on aggregate functions, and PostgreSQL does not guarantee the order in which the conditions of a `WHERE` clause are evaluated. The self-check that asserts "no function of this file writes to `auth.*`" called `pg_get_functiondef(pr.oid)` in a condition of a query over `pg_proc`; inside the transaction (new rows, no statistics) the planner evaluated it on pg_catalog aggregates such as `array_agg` before the schema and name filters. **Read-only evidence collected afterwards:** `pg_get_functiondef` on an aggregate raises 42809 (observed for `array_agg` and `max`); an unfiltered scan raises it; the same query with an ordinary-functions-only filter (`prokind = 'f'`) fenced in a subquery (`OFFSET 0`) runs cleanly over all schemas. (On the committed catalog the original shape happens to run without error, which is why no earlier check could show the problem.) The other `pg_get_functiondef` call in the file takes names from a fixed list of ordinary functions and is not affected.
**What was not checked:** because the file stopped at its last statement, the in-transaction observations (catalog counts, ACL strings, policies, triggers, rate-limit and nonce behavior, anon and non-owner calls) were **not reached**. Nothing from them may be claimed.
**Candidate fix (not applied to the approved file; not executed).** `0005-rev3.1-candidate.sql` (kept next to the dry-run script) differs from the approved file in **one statement** (lines 1041 to 1043 become 1041 to 1047): the candidate rows are first reduced to `prokind = 'f'` functions of the two schemas in a subquery that cannot be flattened (`OFFSET 0`), and only then is `pg_get_functiondef` applied; two RPC names were added to the filter. Everything else is byte-identical (first 1040 lines and the closing lines compared). **Candidate sha256 `8548e27e7c800d9d38f8bb6dca1dcb11f7755785b1e6fa0f0616120f05443e8d`.** The approved rev3 file (`c6400e50…`) is unchanged. The dry-run script verifies whichever hash it is given (`P2_DRY_FILE`, `P2_DRY_EXPECTED_SHA`); running the candidate needs **your approval of that hash**, because the approval was bound to `c6400e50…` and to a single execution.
**Also a lesson for the checks:** the static checker and 293 text-level tests could not see this; only execution did. The same fencing was applied to the observation queries of the dry-run script itself.

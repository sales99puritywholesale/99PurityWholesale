## 3. Findings while writing the tests (not yet confirmed by execution)
1. `last_admin_protected` and `invariant_protected` in the RPCs can only be reached by a **race**: the caller of every revoke/disable must itself be an active admin, so a non-racing call can never remove the last one. The database guard is tested directly (G7); the RPC mapping needs the concurrency suite.
2. `rpc_staff_claim_factor` writes the trigger's message (`sqlerrm`) into the **audit detail** on rejection (not into the response). It is bounded text from fixed trigger messages and only readable by `audit.read` holders, but it is the one place where internal rule names are stored; acceptable, noted.
3. A replay of a successful claim returns `approval_rejected` (the consumed window is rejected by the trigger before the unique key is reached), not `already_approved`; the suite asserts "refused", not the specific code.
4. Tests assume `auth.mfa_factors` accepts a minimal insert (id, user_id, friendly_name, factor_type, status, created_at, updated_at, secret). If hosted requires another column, setup fails loudly (no false pass).

## 4. Why concurrency tests are not executable yet
They need several sessions and therefore **committed** fixtures, and committed staff fixtures conflict with the first-administrator bootstrap rule (both staff tables must be empty) and with your instruction not to create staff records. Safe options: (a) run them on a **local disposable PostgreSQL 17 with the Supabase auth schema** (Docker; you cancelled Docker dependency earlier, so this needs your decision); (b) run them on hosted **before** bootstrap with committed fixtures and a cleanup that needs the owner role to disable the guard triggers (`session_replication_role`), which I have not verified the platform allows; (c) accept the mechanism evidence (G7 and G10 lock checks) plus code review for the first release and test concurrency after bootstrap with two real administrators. I recommend (a).

**Owner factor sequence (`owner-factor-sequence-test.mjs`), hosted, disposable Auth users.** Third and final run: all checks passed. Observed facts (all with real Auth sessions):
1. First factor enrolled at aal1 and never verified; a fresh password-only session verifies it and the token becomes **aal2** (the review's claim is confirmed). The rev1 predicate would grant owner MFA; the rev2 predicate **denies** (verified but unapproved). With a simulated approval row the same token is granted.
2. With an approved factor A and a leftover unverified factor B, a password-only attacker verifies B at aal1 and gets aal2; rev2 denies; **the attacker's aal2 token can delete the approved factor A (HTTP 200)**, leaving no approved factor (the chain documented in the 0005 review; end state: owner privileges denied, `recovery_required`).
3. **New observation:** when the legitimate owner verifies the approved factor A, Auth **removes the leftover unverified factor B** (purge on verification). The attack therefore only works while the leftover factor still exists, that is until the owner's next successful MFA sign-in. This narrows but does not close the window (the attacker needs the owner's password and the secret before the owner next signs in with MFA).
4. Factors **before / during / after a window** (window simulated; predicate mirrors the trigger's factor checks): a verified factor created before the window is not eligible; an unverified one is not eligible; a verified one created during the window is eligible; a verified one created after the window expired is not eligible.
5. **Valid approval:** after approving F1, verified-unapproved leftovers still deny the session; after they are removed the approved factor alone grants.
6. **Deletion of an approved factor** (by a session elevated through it) succeeds at the Auth level (HTTP 200) and the rev2 predicate then denies even if the old aal2 token is still presented; approval history remains (state `recovery_required`).
7. **New observation:** deleting the factor that elevated a session **downgrades that session on the server**: the next deletion with the same (still aal2-claiming) token was refused with `insufficient_aal`; the owner must elevate through a remaining approved factor first.
Cleanup and integrity: every disposable user, identity, factor and profile removed (verified per account); the two validation accounts byte-identical; **all** `auth.users` and `auth.mfa_factors` rows identical before and after (digests and counts: users 2 to 2, factors 1 to 1); no staff members and no organizations created; no registry file left.

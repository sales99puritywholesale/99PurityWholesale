# Staff concurrency testing: design (documentation only)

Status 2026-11-10. **Nothing in this document has been built or run.** No staff record, window, factor or fixture was created; the real administrator was not touched; no audit protection was weakened; no trigger was disabled. This design replaces Part 2 of `P2-CONCURRENCY-TEST-PLAN.md`, which is withdrawn. **No race listed below may be described as verified until the corresponding test has actually run in an isolated environment.**

## 1. What exists and what does not
Verified so far, **sequentially and inside rolled-back transactions** (89 tests): the rules themselves (last-admin guard at trigger level, exclusion in both directions, claim rejection paths, refresh timing, audit atomicity) and that the refresh takes an advisory lock. **Not verified:** that two sessions racing are serialized correctly by those locks. The five races below are therefore **unverified under concurrency**.

## 2. Requirement for the environment
The race tests need several sessions that see each other's **committed** state, with staff rows, enrolment windows, approved factors and audit rows. Committed rows in the shared hosted schema are forbidden (they conflict with the first-administrator bootstrap rule, and the append-only audit table could never be cleaned without weakening it). So the tests must run where **everything can be discarded by dropping the environment**, and where dropping it does not touch audit protections of the real tables.

## 3. Environment options (ladder, weakest isolation first)
| Option | What it is | Isolation | Faithfulness to the deployed objects | Cost and approvals |
|---|---|---|---|---|
| **I. Shadow schema** `p2_staff_conc` in the hosted dev database | a hash-checked, mechanically rewritten **copy** of the staff objects of 0001 (organizations and members only), 0002, 0003 and 0004 | no reference to `public`, `private`, `auth`; no API-role privilege; dropped with `DROP SCHEMA ... CASCADE` (DDL: row triggers, including the copied append-only audit trigger, are not involved and the real audit table is not touched) | tests the **copied** logic; faithfulness is *proved* by the equivalence check in 4.3, not assumed | same approval class as the rate-limit schema test (approved on 2026-11-10 for that suite); needs its own approval for this design |
| **II. A separate, empty, disposable Supabase project** | a new development-only project with 0001 to 0004 applied and real Auth | complete (separate database, separate Auth) | the **deployed** objects, real `auth.users` and `auth.mfa_factors`, real PostgREST/GoTrue tokens possible | a new project (cost, dashboard action by the owner, new credentials kept out of the repository); strongest evidence |
| **III. Local disposable PostgreSQL 17 with the Supabase auth schema** | container | complete | deployed objects | Docker, which is not used in this project by decision; listed only for completeness |
**Recommendation:** build **I** first (cheap, fast, automatable, no new project), with **II** as the final confirmation before production and before the first real administrator exists elsewhere. **III** is excluded.

## 4. Design of option I (shadow schema)
**4.1 Construction (mechanical, reviewable).** A script reads the four migration files **from `supabase/migrations/`** (hash-checked against `migration-hashes.txt`), takes only the objects named in an explicit allow-list (tables `organizations`, `organization_members`, `staff_members`, `staff_roles`, `capabilities`, `role_capabilities`, `staff_mfa_enrolment_windows`, `staff_mfa_factors`, `platform_validations`, `audit_events`; the guard, lock and approval functions and triggers; `staff_gate`, `staff_session_ok`, `mfa_check_ok`, `has_capability`, `step_up_ok`, `write_audit`, `run_auth_structure_check`; the 10 RPCs) and rewrites schema names: `public.` and `private.` become `p2_staff_conc.`.
**4.2 Stand-ins for what lives in `auth`.** Inside the shadow schema, small stub objects replace the three Auth dependencies: `users(id uuid primary key, email text, email_confirmed_at timestamptz)`; `mfa_factors(id, user_id, factor_type, status, created_at, ...)` with the same column names and types the structure check expects; and two shim functions `uid()` and `jwt()` that read the `request.jwt.claims` setting exactly as the platform does. `auth.users` references in the copied DDL are rewritten to the stub. **Nothing references the real `auth` schema.** Because the stub is ours, the structure-check race (5.5) can be driven into a **real failing state** (drop a stub column) safely, which cannot be done on the real table.
**4.3 Equivalence proof (what makes the copy trustworthy).** For every copied function, take the live definition from the deployed database (`pg_proc.prosrc`), apply the same reverse rewrite to the shadow definition, and require **byte equality** after normalizing the schema names and the three auth shims; for every trigger, the same with `pg_get_triggerdef`; for every constraint and index, the same with `pg_get_constraintdef` / `pg_get_indexdef`. Any difference **stops the run** ("the copy is not the deployed logic"). This turns "we tested a copy" into "we tested the deployed logic in another namespace".
**4.4 Isolation proof (same as the rate-limit suite).** Offline text assertions (no reference to `public.`, `private.`, `auth.`, `extensions.`, `storage.`; no grant; no `DO` block apart from the copied self-checks if kept; every created object named `p2_staff_conc.*`, with a negative control that rejects a contaminated copy); at run time revoke all privileges from PUBLIC, anon, authenticated and service_role and **assert from the catalog** that none remain; owner connection only; before and after snapshots of everything else identical; the schema gone afterwards, verified from a fresh connection.
**4.5 Fixtures (inside the shadow schema only).** Stub users `A1`, `A2` (admin), `S1` (support), `P1`, `P2` (plain), `O1` (organization owner of a copied organization `P2CONC`). Admins and S1 are approved through the **copied** window trigger path (bootstrap-style first admin, then the copied RPCs for the rest), with stub factors created after their windows. The real administrator and the real tables are never involved. The copied audit table keeps its append-only trigger **enabled throughout**: the fixtures' audit rows are discarded only by dropping the schema.
**4.6 Race harness.** N plain database connections (default 20 for stress rounds, 2 or 3 for deterministic holds), the owner role, `set local role authenticated` plus `request.jwt.claims` to simulate each caller. Two techniques per scenario: **(a) deterministic hold:** session A runs the operation inside an open transaction and stops before COMMIT; session B starts the competing operation; the harness asserts from `pg_stat_activity`/`pg_locks` that B is **waiting on the expected lock** (advisory lock key, or row lock), then commits A and asserts B's outcome; this proves the *mechanism*, once, reliably; **(b) stress:** 50 to 200 rounds with a start barrier, restoring the fixture state between rounds, to catch interleavings the hold did not consider. A deadlock (SQLSTATE 40P01), a serialization or isolation error that is not the documented 25000 refusal, or any round that violates an oracle is a **failure**. Each scenario also runs once at `REPEATABLE READ` and must be **refused** with the documented error, never silently succeed.

## 5. Scenarios, oracles and what each proves
**5.1 Last-admin protection** (copied triggers `guard_last_admin_lock`, `check_last_admin`, lock `m1:last_admin`). Races: A1 revokes A2's admin vs A2 revokes A1's; A1 disables A2 vs A2 disables A1; A1 demotes A2 while A2 is deleted (cascade through the user stub); a third admin being added concurrently with a demotion. *Hold test:* A holds after its delete; B must wait on `m1:last_admin`; after A commits, B returns `last_admin_protected` (or `invariant_protected` for the disable path). *Oracles for every round:* at least one active admin exists at every observation; exactly one of two mutual operations succeeds; audit has exactly one success and one denied row; no deadlock; the FK-cascade case ends with one admin. *Today:* unverified.
**5.2 Staff/member exclusion** (per-user advisory lock, both guards). Races: `rpc_staff_add_member(P1)` vs inserting P1 as an organization member; reinstating a disabled staff member vs inserting a membership; both orders; a user with a **disabled** staff row. *Hold test:* A holds the per-user lock inside the add; B's membership insert must wait on the same key. *Oracle:* a user is never simultaneously a staff row (any status) and an active member; the loser gets `organization_member_conflict` / SQLSTATE 23514; lock order (`m1:last_admin`, then organization row, then per-user) never produces a deadlock. *Today:* unverified.
**5.3 Double claims** (window row locked `FOR UPDATE` in the approval trigger, `unique(window_id)`). Races: two `rpc_staff_claim_factor` calls on one window with **two different** factors; the **same** factor twice; claim vs window revoke; claim vs expiry boundary (window expiring during the call). *Hold test:* A holds after the approval insert; B's claim must block on the window row lock, then be rejected as consumed. *Oracle:* exactly one approval row per window; the window is consumed once; a window is never both consumed and revoked (the table constraint is the backstop); the loser sees `approval_rejected`/`already_approved`; the winner is never left unapproved. *Today:* unverified.
**5.4 Double enrolment-window creation** (partial unique index `one open window per target`). Races: two `rpc_staff_authorize_enrolment_window` for one target (different authorizing admins); authorize vs revoke; authorize while an **expired but unconsumed** window exists (it still counts as open: documented behavior). *Hold test:* A holds after the insert; B must block on the unique index and then get `window_already_open`. *Oracle:* at most one open window per target at every observation; two audit outcomes consistent with the winner. *Today:* unverified.
**5.5 Structure-check refresh races** (advisory lock `p2:structure_check_refresh`, re-check under the lock). Races: 20 concurrent `rpc_my_staff_context` calls from active staff with a check older than 12 hours; the same with a **failing** structure (stub column dropped) racing with a passing session; a refresh racing with `staff_session_ok()` evaluations (a failed refresh must deny immediately, a passed one must not grant by itself). *Hold test:* A holds inside the refresh; B must wait on the lock, then **not** run a second refresh (it re-checks and finds a fresh row). *Oracles:* exactly one refresh run per stale period (one row update, `checked_at` advanced once); every caller gets a consistent answer; a failing result overwrites a passing row and denies staff on the next call; the refresh never grants capability. *Today:* unverified; option I is the only way to test the failing case at all without damaging the real table.

## 6. Limits of option I (state plainly in every report)
It verifies the **copied** logic in a different namespace, with stand-ins for Auth; it cannot detect a difference caused by the real `auth` schema's own triggers, by Supabase's role setup, or by PostgREST. The equivalence proof covers function, trigger, constraint and index definitions, not the platform. Option II closes that gap. Neither option tests real Auth tokens through the race (token handling is covered by the PostgREST suite).

## 7. Sequence and approvals
1. Build the construction script and the **offline** isolation and equivalence-text self-tests (no database): possible without further approval, and already the pattern of `rate-limit-concurrency-isolated.mjs`. 2. Approval to create `p2_staff_conc` on hosted dev and run the hold tests, then the stress rounds. 3. Run, verify the schema is dropped and the snapshots of everything else are identical. 4. Decide on option II. Until step 3 has run, every statement about staff concurrency stays **unverified**.
**What this design deliberately does not do:** create any record in the shared `public`/`private` schemas, disable or weaken any trigger (including the audit and last-admin triggers), touch the real administrator or bootstrap, delete or update any real audit row, or use Docker.

## 0. Findings from the inspection (revision 2)
1. **Documents were stale.** Corrected in this revision (documentation only, history preserved): `P2-2-P2-4-DESIGN.md` and `P2-2-STRUCTURE-CHECK-AND-BOOTSTRAP.md` now carry a dated status block with the actual state (0001 to 0004 applied and synchronized, 0005 rev3.1 reviewed and dry-executed but unapplied, recovery design as approved, the verification still outstanding) and an inline marker on each superseded statement; the old text remains.
2. **`run_auth_structure_check()` finds the table by string literal** (`table_schema = 'auth'`, `nspname = 'auth'`). A mechanical identifier rewrite would leave the shadow check inspecting the real table. **Resolved in the offline tool:** the rewrite classifies every site, including schema-name literals used in catalog queries (17 across the five files), and the run-time equivalence check applies the same rewrite to the live definitions.
3. **Default privileges.** 0001 contains seven `ALTER DEFAULT PRIVILEGES` statements, one of them global (`revoke execute on functions from public`). They are **excluded** from the shadow and counted; the run compares `pg_default_acl` at every checkpoint.
4. **Dependencies on `auth`:** `auth.users`, `auth.uid()`, `auth.jwt()`, `auth.mfa_factors` only (no `extensions.`, no `storage.`).
5. **Advisory locks are database-wide.** The shadow copies would take the same keys as the live functions; resolved by a declared namespace rewrite (total sites: 8 for rev3.1, 17 for rev4, **20 for rev5**) with its own proof (P8).
6. **Design gap found earlier (owner who lost both factor and codes)** and **last-write-wins operator authorization**: both are now decided (D-V1, D-V2) and specified for rev4.
7. **Time cannot be moved in a shadow.** "24 hours later" is simulated by **inserting rows with backdated timestamps** as the owner role and by adjusting rows of unguarded tables; guarded rows are never updated to move time. For operator-origin requests the cool-off is anchored at the second approval, so the backdated row carries `approved_at` backdated as well (the check constraint is satisfied by construction).
8. **A shadow is not a separate database.** The dossier lists what is shared and why it does not interfere (section 8) and what remains different (section 9).

## 7. Application-level email abuse controls: design (separate from the SQL rate limits; nothing built, no provider, no real email)
**7.1 Principle.** The database cool-down only answers "may a send happen now". Everything that makes a send safe, generic and non-abusable lives in the application, in a pure, tested module with a mailer interface; the default mailer is a null or fake one.
**7.2 Components (all in `src/lib/portal/recovery-mail/`, pure TypeScript except two thin adapters).**
1. `normalizeEmail()` shared with the throttle key derivation (single function, so the key and the lookup cannot disagree: lower-case, trim, Unicode NFKC, reject control characters and over-length, no plus-tag stripping); property tests for idempotence and key equality.
2. `clientAddress(request)`: derives the address **only** from the platform's trusted header (never from a client-supplied `X-Forwarded-For` chain), groups IPv6 by /64, returns `unknown` when untrusted, and the throttle treats `unknown` as its own shared bucket (strict). Tests with spoofed headers.
3. `verifyChallenge(token)`: server-side bot-challenge verification behind an interface (vendor chosen later, D-P24-14); **fails closed**; its result is never revealed to the caller.
4. `requestPasswordReset(email, request)` orchestration in a fixed order with constant work: challenge, normalize, key derivation, throttle RPC, account lookup by the identity provider's recovery endpoint (which sends to the address on file), **coalescing** (skip the send while an unexpired unused link younger than 60 minutes exists), mailer call, minimum response time padding, generic response. Every outcome returns the same status, body and timing class.
5. `SendBudget`: per-hour and per-day counters (in the database through a server-only function or the existing counter table via a new bucket in a later migration; to be decided) with alert thresholds; alert, never hard-stop.
6. `ProviderFailurePolicy`: a provider error is logged as a code, the response stays generic, and a metric is incremented; optional server-side cool-down release only if D-P24-13 chooses it.
7. Link rules: recovery link lifetime verified at configuration time (at least 60 minutes), single use, redirect target restricted to an allow-list, session invalidation after reset, **a password reset never satisfies staff or owner MFA** (the next token is aal1 and the existing gates apply).

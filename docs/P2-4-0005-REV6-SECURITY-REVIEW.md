## 2. Fail-closed factor reads (decision 2): what the draft does
- **Structure check:** `private.auth_structure_ok()` is the predicate of `private.mfa_check_ok()` (0002) without its caller-specific part: a `passed` row named `auth_mfa_factors_shape`, at most 24 hours old and not future-dated; any error is false.
- **Unknown is NULL, never empty:** `private.owner_verified_factor_ids(user)` returns NULL when the argument is NULL, the structure check is absent, stale, failed or future-dated, any factor row of the user has a NULL id, a NULL or unrecognized status (anything except verified/unverified) or a NULL or unrecognized type (anything except totp/phone/webauthn), or on any error. An empty array means only "the database read this user's factors and none is verified".
- **Every owner-path consumer fails closed:** `owner_factor_state` returns `unknown`; `owner_mfa_ok` returns false (also without the check); the factor approval gate raises on NULL; the window gate refuses a NULL snapshot and a count that differs from the database's; the order insert and completion guards refuse NULL; `rpc_staff_authorize_owner_mfa_window`, the extension RPC, begin and complete return `unknown_state`; the overview returns NULL (JSON null) rather than 0; the factor-loss review refuses with `structure_check_required` instead of returning a partial list.
- **No other direct reader:** only `owner_verified_factor_ids`, `owner_factor_state`, `owner_mfa_ok` and the factor gate (the row of the factor itself) read `auth.mfa_factors`; the self-check and the static checker (rule P29) assert it, and P29 also flags `coalesce()` over the helper.
- **Consequences stated plainly:** (a) **availability:** there is no scheduler; when the structure check is older than 24 hours owner MFA (and every owner-only policy) is denied until a staff call refreshes it. A scheduled refresh is an operational decision outside this file. (b) **the table is not an officially specified interface;** the check is a mitigation against drift, not a guarantee. (c) an unknown state keeps the owner cancellation lock and refuses exception use, but never destroys an exception (defect X11, below).

## 3. Factor removal (decisions 1 and 6)
- **Order:** an active operator (capability, fresh step-up) orders the removal for the owner's OPEN recovery window of a pending, unexpired request past its cool-off. The **database** reads the exact verified factor ids and stores them; the operator receives them from the database (never supplies them). One live order per window; idempotent; expires with the window; cancelled with a revoked window; expired lazily with an audit row.
- **Execution is manual, outside the database** (Dashboard). Nothing in this file writes to or calls any Auth interface.
- **Completion:** `rpc_staff_complete_factor_removal(order_id)` takes only the order id. The database reads the state itself: unknown refuses (no attempt consumed); any verified factor outside the snapshot makes the order stale (FAILED, new order needed); a snapshot factor still present is a refused attempt (5, then FAILED); only "no verified factor at all" completes. **The order guard re-reads the state at the transition**, so a direct update cannot complete an order. On success the order, the window and (once) the request are recorded together; the window update guard requires a completed order of that window; the request marker guard requires a completed order of that request.
- **Per-window verification:** a recovery window that opens with no verified factor is verified at once (`none_needed`); otherwise only a completed order verifies it (`manual`). The factor gate approves a factor only in a verified window; request completion needs the very window that completes it to be verified (fixes D2: a leftover factor of an earlier window makes the next window need its own verified removal).
- **What the database verifies and what it does not:** it verifies the OUTCOME (no verified factor remains). It does **not** verify who removed what, through which interface, that the Dashboard action touched the right user, or that no other user's factor was deleted; the detective review `rpc_staff_list_owner_factor_loss` reports owners whose factors vanished without a sanctioned request. The method on an order is always `manual`.
- **Known limitation found while drafting:** if factors are removed BEFORE the order is begun (a procedure deviation), the window cannot be verified (no order can be created with zero factors); the operator opens the next window, whose snapshot is zero and verifies at once. It costs one window and leaves the deviation visible in the audit.

## 4. Stranded-owner exception (decisions 3 and 4)
Confirmed in the SQL (all static): lifts **only** the per-owner quota (`operator_recovery_target`), explicitly (`p_exception_id`), for one operator-initiated request; the operator quota, open-request check, owner lock, two-person approval, 24 hour cool-off, windows, step-up and MFA enrolment are untouched. Different, active, capable operators with fresh step-up for request and grant (`staff_gate(..., true)`), both rechecked at grant and again at consume (the update guard and the request insert guard). The stranded state is rechecked at request (RPC and insert guard), grant (RPC and update guard), and consume (RPC before the insert and the insert guard before the row exists). State machine: `requested → granted | expired | cancelled`, `granted → consumed | expired | cancelled`, final states immutable; expiry is enforced at the transitions (24 hours to grant, 72 hours to use); the status/shape, two-person, grant-group and expiry rules are table constraints. Ownership is composite (`(id, user_id)` keys in both directions); the consuming request carries `exception_id` (unique), so one request consumes at most one exception and an exception is consumed at most once; consumption and insertion share one sub-transaction. One open exception per owner and one live exception per stranded request (partial unique indexes); an expired or cancelled one can be requested again within the cap of 2 per owner per 30 days. A completed recovery or a changed state closes outstanding exceptions (claim and lazy closing; audited, fixed codes). All transitions write audit rows.
**Defects found and fixed while drafting (all in rev6 text):** X1 consumption order (settled by `exception_id` on the request and validation in the BEFORE INSERT guard), X2 to X10 as approved, **X11** a stale structure check would have cancelled every granted exception (unknown now only refuses use), an unknown state would have dropped the owner cancellation lock (now kept), the factor-loss review would have silently omitted unknown owners (now refuses), a dead closing code (`recovery_completed`) was removed.

## 5. Windows (decision 5)
`windows_issued` 0..5 and `extra_windows_granted = greatest(windows_issued - 3, 0)` (constraint); the standard RPC stops at 3 (RPC and update guard); the extension RPC is the only path to the fourth and fifth, atomic with its window insert, step-up gated, with an audited reason (text in the row only), requiring a window of the request with verified removal, an unexpired request past its cool-off with at least 5 minutes left; the window insert guard requires `windows_issued = (number of window rows) + 1`, so counters and rows cannot diverge; a window cannot end after its request (guard and RPC `least(...)`); no statement decreases a counter; request expiry and cool-off are immutable in the update guard. Concurrency: locks (2) and (3), the request row lock, the one-open-window index and the cap check.

## 7. Break-glass and erasure (decision 7)
Hard deletion of Auth users with history fails (twelve `ON DELETE RESTRICT` foreign keys among the six tables, self-checked on the catalog); no erasure code exists. Break-glass has **no code path** in rev6: it cannot create or approve a factor, satisfy owner MFA or step-up, shorten the cool-off, change a quota or a counter, or touch the exception, order or window tables. The stranded exception removes the need for an emergency-allowance migration. See `docs/P2-4-RECOVERY-BREAK-GLASS.md`.

## 8. What cannot be enforced or tested offline (explicit list)
1. **That PostgreSQL accepts the SQL** (syntax, types, PL/pgSQL, the circular foreign key created by `ALTER TABLE`, the DO block). Paren and `$$` balance and the text checkers were run; nothing more.
2. **Runtime satisfaction of the constraints** by the RPC statements (for example the interplay of `windows_bounded`, the counter-equals-rows guard and the sub-transaction order `update` then `insert`).
3. **Trigger behavior** and error mapping (23514, 23505), including reading the request row inside a BEFORE INSERT trigger and the stable helpers seeing the statement snapshot.
4. **Concurrency:** serialization by locks (1), (2), (3) and row locks; no two exceptions or extensions or orders under race; **designed and statically ordered, never executed**.
5. **The isolation refusal** at REPEATABLE READ and SERIALIZABLE.
6. **Real Auth behavior** (factor purge on verification, session downgrade on deletion, enrolment at aal1 after removal, the real shape of `auth.mfa_factors`, soft delete) and **the structure check on a real project** (24 hour freshness, the refresh path).
7. **P1** (PostgREST transaction end, `db-tx-end`, `Prefer: tx=rollback`): unresolved by instruction.
8. **Manual removal:** that the operator removes only the intended user's factors is a human act; the database verifies the outcome only.
9. **Time-dependent rules** (24 hour cool-off, 72 hour deadline, 30 day lookback, expiries) are tested as text and as pure models only.
10. **Operational controls** (two accounts are two people, identity verification, break-glass decisions, scheduled structure-check refresh).

## 9. Unresolved risks
Availability coupling of owner MFA to a fresh structure check; the `auth.mfa_factors` read is an unspecified interface; manual removal can hit the wrong user (detected, not prevented); removal before ordering wastes a window; the enrolment race inside an open window; audit volume from refusals; P1; collusion of two accounts; custody of the database owner credential; the stranded owner has no instant path beyond windows, a new request (quota) or an exception; the application throttle is not a boundary and has no new approved values.

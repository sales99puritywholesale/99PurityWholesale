# Concurrency test plan (planning only: nothing here was created or executed)

Status 2026-11-10. Boundaries from the approval: no Docker, no local PostgreSQL, **no fixtures created without separate approval**. Every fixture below is a proposal with its own approval gate. The executable bodies are not written; the scenario list lives in `supabase/review/tests/rpc-concurrency-tests.mjs` (refuses to run).

Common rules for every run: strict TLS and exact project reference (`semtmllmwhxznxechfsk`); a **registry file** written before the first fixture is created, naming every id; cleanup by id **and** name pattern only; before/after snapshots of catalog, row counts, Auth digests and migration history (the same `snap()` used by `rpc-transactional-tests.mjs`) with a stop-and-report on any difference; no secrets printed; sessions are plain database connections that simulate callers with `set local role` + `request.jwt.claims` (no Auth traffic needed, so no anon key is read).

## Part 1: rate-limit and nonce concurrency (non-staff fixtures only)
**Why a fixture is needed at all.** The functions are in 0005, which is **not applied**; concurrency needs committed objects visible to many sessions. To avoid applying 0005 itself, the proposal is a **disposable schema** `p2_conc_test` created from the rate-limit and nonce sections of 0005 (tables, `rate_limit_hit`, `consume_nonce`, with `private.` rewritten to `p2_conc_test.` by a hash-checked text transformation; nothing else from 0005, no owner-MFA objects, no policies, no grants to API roles).
**Fixtures (all new, all removable by `drop schema p2_conc_test cascade`):** the schema; 3 tables; 3 functions; seeded policy rows for the six buckets; no users, no staff, no organizations, no Auth rows. Keys are random 32-byte values generated per test.
**Setup:** (1) snapshot; (2) write registry (schema name, creation time, transformation hash); (3) create schema in one transaction; (4) verify object list equals the expected list.
**Scenarios and assertions** (N = 50 concurrent connections, each calling once unless stated; barrier: all connections `begin`, then a shared start signal):
| # | Scenario | Assertions |
|---|---|---|
| R1 | same key, bucket `recovery_code` (max 5) | exactly 5 `allowed=true`; 45 `false`; row `attempts` = 6; `blocked_until` set once and not later than `now + block_secs`; no exception |
| R2 | 50 distinct keys, same bucket | 50 `allowed=true`; 50 rows |
| R3 | same key at the boundary: row pre-set to `attempts = max`, window just elapsed | exactly one call resets the window; allowed count = max; no double reset |
| R4 | blocked key hit by 50 sessions | all denied; `blocked_until` unchanged (no extension); `attempts` unchanged |
| R5 | the throttle pair (email key, address key) from 50 sessions, shared address key | per-key limits respected independently; no deadlock (a fixed key order avoids it; assert completion within 10 s) |
| R6 | cleanup bound: seed 500 idle rows older than 2 days, then 12 sequential hits | each call deletes at most 50; zero stale rows after 10 calls; a row locked by another session is skipped (the hit returns within 1 s) |
| N1 | `consume_nonce` same hash from 50 sessions | exactly one `true`, 49 `false` |
| N2 | expired nonce row, 50 sessions | exactly one `true` (reuse of the expired row), the rest `false` |
| N3 | consume inside a transaction that rolls back | the nonce is **not** consumed; the next call returns `true` |
| N4 | same hash, two purposes | independent (both `true`) |
| N5 | invalid inputs under load (31-byte key, ttl 5, unknown bucket) | all raise 22023, no row written |
**Cleanup:** `drop schema p2_conc_test cascade`; verify with the catalog snapshot that functions, relations, columns, policies, triggers, ACLs, row counts, Auth digests and migration history equal the **before** snapshot byte for byte; delete the registry only then. If any step fails: stop, print the registry and the exact `drop schema` statement, change nothing else.
**Approval needed:** creation of the disposable schema on hosted dev (a committed catalog change that is removed again) and the run itself. Nothing touches Auth or staff.

## Part 2: last-admin, staff exclusion and other staff concurrency (temporary staff fixtures)
**Constraint.** Committed staff fixtures conflict with the bootstrap rule (both staff tables must be empty) and need 0003+0004 applied (the RPCs and audit table). Two safe orderings, each needing its own approval:
**Ordering X: before bootstrap, after 0003+0004 are applied.** Staff tables are empty. Fixtures are the only staff. Cleanup must delete the **last** admin, which the guard forbids, so cleanup uses the table owner to `alter table public.staff_roles disable trigger staff_roles_last_admin_check` (and the three sibling triggers) in the cleanup transaction, deletes the fixture rows, **re-enables** them, and verifies `tgenabled = 'O'` for all four. Failure mode: a crash between disable and enable leaves the guard off; mitigated by doing disable, delete and enable in **one transaction** (DDL is transactional: a crash rolls the disable back) and by the final catalog snapshot.
**Ordering Y: after bootstrap.** A real admin R exists. Fixtures are extra staff; cleanup deletes only fixture rows (allowed, R remains). The two-admin race scenarios need exactly **two** active admins: with R plus A, B the guard is never triggered. To reach the boundary, R is **temporarily set to `disabled`** by the owner role (allowed while A and B are active) and restored afterwards. This touches the real administrator's row and must be separately approved; I recommend Ordering X.
**Fixtures (identical in both orderings):** disposable Auth users `p2conc-<role>-<hex>@example.test` (insert into `auth.users`/`auth.identities` as the owner role; no GoTrue calls): A1, A2 (admin), S1 (support), P1, P2 (plain), O1 (organization owner, with one test organization `P2CONC-TEST` and one active owner membership). Approved factors for A1, A2, S1 inserted through the **real** 0002 window trigger path (window by owner role with `authorized_by` null for the first, then by RPC), each factor row inserted into `auth.mfa_factors` as the owner role with the exact columns the transactional suite uses (and verified to be accepted there first). All names carry the `p2conc-` prefix and ids are in the registry.
**Setup:** (1) snapshot; (2) registry; (3) users; (4) organization and membership (O1 only); (5) staff and approvals; (6) assert `staff_session_ok` is true for each simulated caller; (7) assert preconditions (exactly two active admins for the race scenarios).
**Scenarios** (50 rounds each unless stated; each round restores the fixture state by the owner role between rounds):
| # | Scenario | Assertions per round |
|---|---|---|
| S1 | A1 revokes A2's `admin` while A2 revokes A1's (two connections, barrier) | exactly one `revoked`, the other `last_admin_protected`; exactly one active admin afterwards; two audit rows (one success, one denied) |
| S2 | A1 disables A2 while A2 disables A1 | one `updated`, one `invariant_protected`; one active admin remains |
| S3 | A1 demotes A2 while a third admin is concurrently added | never zero active admins at any observation; counts consistent with audit |
| S4 | `rpc_staff_add_member(P1)` vs inserting P1 as an organization member (owner role) at the same instant | never both staff and active member (the guard takes the same per-user advisory lock) |
| S5 | 20 concurrent `rpc_my_staff_context` calls with a structure check older than 12 h | exactly one check row update (`checked_at` advanced once); all callers get a consistent answer; no deadlock |
| S6 | two `rpc_staff_claim_factor` calls for one window with two different factors | exactly one approval row; window consumed once; the other call `approval_rejected` |
| S7 | two `rpc_staff_authorize_enrolment_window` calls for one target | exactly one window; the other `window_already_open` |
| S8 | `rpc_staff_set_status` suspend of S1 racing S1's own `rpc_staff_directory` | after commit S1 is refused; no half state |
| S9 | all of the above at `REPEATABLE READ` | refused with the guard's isolation error (25000), never a silent pass |
**Cleanup (Ordering X):** in ONE transaction: disable the four last-admin triggers, delete fixture staff rows (roles, approvals, windows cascade), re-enable, assert enabled; delete memberships, the test organization, factor rows, identities, users by id and pattern; commit; then the catalog/row/Auth/migration-history snapshot must equal the before snapshot (audit rows written by the RPCs are removed too: `audit_events` is append-only, so the test requires the owner to `alter table ... disable trigger` for the audit guard during cleanup, or accepts that audit rows of fixtures remain; **this is an open point needing your decision**: the append-only rule is exactly what prevents clean removal). **Cleanup (Ordering Y):** as X but no trigger disabling for the last-admin guard; R's status restored first and verified.
**Approval needed (separately, each):** applying 0003+0004 (not requested here); Ordering X or Y; the temporary disabling of triggers in cleanup; the treatment of fixture audit rows.

## UPDATE 2026-11-10: approved restrictions (these SUPERSEDE the parts above they contradict)
**Withdrawn from this plan:** Ordering Y (never: it disabled the real administrator); every cleanup step that disables or alters a trigger, in particular the audit triggers and the last-admin triggers; any deletion or update of audit records; any temporary staff record in the shared hosted development schema. **Audit events remain append-only and test audit events must roll back**: the transactional suite already guarantees this (its audit rows exist only inside the rolled-back transaction and the post-run snapshot proves `audit_events` is empty).
**Part 2 (staff concurrency: last-admin, staff/member exclusion, structure-check refresh, window races): DEFERRED.** Nothing in it may be claimed as verified. What exists: the guards are tested directly and sequentially inside the rolled-back transaction (last-admin delete/disable/demote, exclusion in both directions, refresh timing and lock presence), which proves the rules and that the locks are taken, **not** that two sessions racing are serialized correctly. A genuinely isolated approach is required before this can be tested (a copy of the staff tables, functions and triggers in a disposable schema, with the same isolation proof as Part 1, or a separate disposable database); it needs its own design and approval. Until then, **the following remain unverified under concurrency:** `rpc_staff_revoke_role` and `rpc_staff_set_status` against the last admin, `rpc_staff_add_member` against organization-member insertion, `rpc_staff_claim_factor` and `rpc_staff_authorize_enrolment_window` double submission, `rpc_my_staff_context` refresh under simultaneous calls.
**Part 1 (rate limit and nonce): DEVELOPED, NOT RUN.** `supabase/review/tests/rate-limit-concurrency-isolated.mjs`. Isolation is demonstrated, not asserted: (a) the schema content is the rate-limit and nonce sections of 0005 with `private.` rewritten to `p2_conc_test.`; (b) an offline self-test (**executed, passes**, with a negative control that rejects a contaminated copy) proves the text references no other schema, contains no grant, trigger, policy, DO block, drop or extension; (c) at run time all privileges of the schema and its objects are revoked from PUBLIC, anon, authenticated and service_role, and the script **asserts from the catalog** that none remain; (d) it connects only as the owner role (no JWT claims, no role switching, no Auth traffic, no anon key); (e) before and after snapshots of everything outside the schema (functions, relations, columns, policies, triggers, default privileges, row counts, Auth digests, migration history, schema list) must be identical, and the schema must be gone. Default concurrency is **20** sessions (the direct connection limit of a small instance makes 50 risky; `--n` up to 60 on request). Scenarios R1 to R6 and N1 to N5 as tabulated above, with the assertions implemented. **Approval needed:** creation and drop of `p2_conc_test` on hosted development and the run itself (`--authorized-disposable-schema`, `--authorized-read-env-local`).

## EXECUTED 2026-11-10: isolated rate-limit and nonce concurrency (Part 1)
`rate-limit-concurrency-isolated.mjs`, hosted development project, schema `p2_conc_test`, **20 concurrent sessions**. Final (second) run: **38 of 38 checks passed**. The first run created the schema, passed the isolation checks, then failed on a SQL mistake in my own privilege-check query (a correlated subquery inside an aggregate); its clean-up ran, all 10 after-cleanup comparisons passed, and the second run followed after the stale registry was removed.
**Isolation (observed from the catalog, before any scenario):** the schema contained 8 relations; every other schema's functions, relations, policies, triggers, row counts, default privileges, Auth digests, migration history and the schema list were identical to the snapshot taken before creation (11 checks); **no API role (anon, authenticated, service_role, PUBLIC) held any privilege on the schema, its tables or its functions** (schema ACL `{postgres=UC/postgres}`); every object owned by `postgres`. The text of the copied SQL (the rate-limit and nonce sections of 0005, `private.` rewritten) had passed the offline isolation self-test: no reference to public, private, auth, extensions or storage; no grant, trigger, policy, DO block, drop or extension; negative control rejects contaminated copies.
**Race outcomes (all invariants held):** R1: 20 simultaneous attempts on one key, **exactly 5 allowed**; the 6th attempt set the block and the counter stopped at 6; a second wave of 20 was entirely denied with the counter and the block unchanged (no lockout amplification). R2: 20 distinct keys, all allowed. R3: window elapsed under load, **exactly 5 allowed**. R4: a pre-blocked key under load, all denied, state unchanged. R5: the per-email cool-down under load, **exactly 1 allowed**; the per-address quota across 20 distinct emails, **exactly 20 passed both buckets**, no deadlock. R6: 500 stale rows removed **at most 50 per call and gone after 10 calls**; a row locked by another session was skipped (a concurrent hit returned in 152 ms and the row remained). N1: 20 simultaneous consumptions of one nonce, **exactly one true**. N2: an expired nonce reused **exactly once** under load. N3: a consumption in a rolled-back transaction did not burn the nonce. N4: purposes independent, replay false. N5: invalid inputs raised 22023 and wrote nothing.
**Clean-up (verified from fresh connections):** the schema was dropped; the schema list equals the pre-run list; functions, relations, policies, triggers, row counts, default privileges, Auth users, identities, factors and migration history identical to the snapshot taken before anything was created (10 checks). No staff or organization fixtures were created; no registry file remains.
**Not covered:** 20 sessions, not 50 (connection limit); the copy of the functions in a schema other than `private` (identical text apart from the schema name, by construction); the application contracts of the throttle; staff concurrency (design only: `P2-STAFF-CONCURRENCY-TEST-DESIGN.md`).

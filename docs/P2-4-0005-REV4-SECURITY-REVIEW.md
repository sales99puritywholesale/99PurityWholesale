## 4. Function-by-function review of the new and changed functions
Common properties of all 29 functions: owner `postgres`, `search_path` pinned to empty, no dynamic SQL; the 24 SECURITY DEFINER functions are 10 in `private` and the 14 `public.rpc_*`; the 5 invokers read only `NEW`/`OLD` or the caller's JWT. Expected ACLs: private helpers `{postgres=X/postgres}` except `my_mfa_owner_org_ids` (plus `authenticated`); the 13 owner and operator RPCs plus `authenticated`; the throttle plus `anon` and `authenticated`; tables `{postgres=arwdDxtm/postgres}` only; the migration's final self-check would assert these (not observed).
**`close_expired_recovery_requests(user, actor, kind)`** (definer, not executable by API roles): converts open requests past `expires_at` to `expired` and writes one audit row each (`owner.mfa_recovery.expire`), so no state change is silent. Called under the owner's recovery lock only.
**`guard_owner_recovery_request_insert`**: active owner target, never staff; owner-code requests are created pending; operator requests are created `awaiting_approval` by an active, capable staff member, and only for an owner with an approval history (state none means first enrolment applies).
**`guard_owner_recovery_request_update`**: the lifecycle state machine (awaiting to pending once with the approval group, cool-off and expiry set together; open to cancelled or expired; pending to completed; `windows_issued` plus one while pending); every other change refused; finished requests immutable.
**`guard_owner_mfa_window_insert`**: as rev3.1 plus: recovery windows require the request (pending, cool-off elapsed, unexpired, approved by a different account for operator origin, 1 to 3 windows issued) and the operator capability at the instant of insertion.
**`guard_owner_mfa_window_update`**: identity, authorizer, reason, request link and timing immutable; consumed and revoked outcomes final; the revocation trio set only with the revocation.
**`guard_owner_mfa_factor_insert`**: rev3.1 plus one check: a recovery window is usable only while its request is pending and unexpired. Everything else byte-identical.
**`rpc_staff_authorize_owner_mfa_window`**: gate with step-up; validation before locks; lock order recovery then window; closes expired requests; refuses an active window; closes a lapsed one with a recorded revocation and audit; `none` gives a first window; otherwise a **pending** request is required: `recovery_awaiting_approval` (second operator missing), `recovery_cooling_off`, `factor_removal_required` (a verified factor still exists), `recovery_window_limit`; the window and the issued-counter increment happen in one sub-transaction (a rejected insert does not waste an issuance). Every outcome audited.
**`rpc_staff_revoke_owner_mfa_window`**: gate with step-up, reason, window lock; revokes the active or lapsed window with a recorded revocation; refuses a consumed one.
**`rpc_owner_open_factor_window`**: as rev3.1 plus `window_already_open` and recorded lapse. **`rpc_owner_revoke_factor_window`**: owner revokes only their own `additional` window; approved session and fresh step-up; operator windows are not revocable by the owner.
**`rpc_owner_claim_factor`**: takes the recovery lock, then the window lock; the trigger does eligibility; a recovery window completes **its own request by id** and voids unused codes; messages of the trigger are never returned.
**`rpc_owner_recovery_request`**: throttle first (returns, never raises), generic refusal for non-owner and staff, recovery lock, lazy expiry, owner-cancellation lock (24 h, either origin), one open request, code lookup under row lock, per-user hourly throttle before consuming, then **one captured instant** for `created_at`, `cooloff_until` and `expires_at` (fixing the rev3.1 defect), counter cleared on success, audit.
**`rpc_owner_recovery_cancel`**: the owner cancels an awaiting or pending request of **either origin**; recorded cancellation (who, when); starts the 24-hour lock; audit with origin.
**`rpc_staff_initiate_owner_recovery`** (operator 1): gate with step-up; validation (method list, reference pattern, reason) before any lock; operator lock then owner lock; target must be an active owner (identical refusal for staff, non-owner, unknown); state none gives `first_enrolment_applies`; owner-cancellation lock, one open request; **quotas from durable rows** (`throttled` with `retry_after_secs`); inserts `awaiting_approval` with a 72-hour deadline; audit with method and reference.
**`rpc_staff_approve_owner_recovery`** (operator 2): gate with step-up; validation before locks; owner lock; lazy expiry; refusals (`request_not_found`, `request_expired`, `request_not_awaiting`, `self_approval_not_allowed`, `target_not_eligible`, `state_changed`, `verification_ref_reused`, `notarization_not_sufficient`) each audited; one update sets status, approver, approval time, reason, second method and reference, cool-off and expiry from one instant; a constraint violation is mapped to `approval_rejected`.
**`rpc_staff_cancel_owner_recovery`**: any capable operator with step-up cancels an open request with a reason (stored in the row, not in the audit); no owner lock.
**`rpc_staff_owner_mfa_overview`**, **`rpc_my_owner_context`**: read-only views (the first audited; operators only see ids, methods and references; the owner sees only the status, never operators' identities).

## 5. Concurrency: lock hierarchy, deadlocks, rollback (argued by reading; **not tested**)
**Hierarchy (documented in the file).** (1) per-operator advisory lock (`p2:operator_recovery:<id>`, initiate only); (2) per-owner recovery lock (`p2:owner_recovery:<id>`: every recovery operation, window authorization, claim, code issuance); (3) per-owner window lock (`p2:owner_window:<id>`: every window operation); (4) row locks, always windows before requests inside authorize and claim. **Argument:** any two functions that touch both windows and requests take lock (2) first, so they are serialized per owner and cannot interleave; functions that touch only windows (revoke, open own window, revoke own window) take lock (3) before the window row and never wait for (1) or (2); initiate takes (1) then (2) and no function holding (2) ever waits for (1); different owners and different operators do not contend. A wait cycle would need two functions acquiring the same two resources in opposite orders; none does. **Interaction with the staff hierarchy of 0002** (`m1:last_admin`, organization row, per-user): rev4 functions take none of those locks. **The argument is not evidence:** scenarios CC-21 to CC-33 (hold tests, a pairwise matrix and instrumented lock order) exist to test it in an isolated environment.
**Rollback.** Each RPC runs in the caller's transaction. Operator quotas derive from rows, so a rollback removes the row and its quota consumption together. The owner-code throttle counters persist across refusals because refusals are returned results; an unexpected error (deadlock victim, statement timeout, a cancelled request) rolls back the counter increment with the whole call, **with no effect and no information released**. Residual: a client that aborts mid-call can retry without the failed attempt being counted; the effect of that attempt did not happen either.
**Time of check versus time of use.** An approver who is suspended in the same millisecond window between the gate check and the update can still complete that one approval; the window insert trigger re-verifies the operator when a window is later authorized. Accepted, low.

## 6. Privacy and audit
Audit details contain: ids, window and request ids, kinds, origin, method names, case references, timestamps, status reasons from a fixed vocabulary. They never contain free text, hashes, tokens, secrets, identity documents or personal data. The reference pattern (letters, digits, `. _ : / # -`, 1 to 80 characters) makes it hard to place a name or document content in a reference, but a value such as `JohnSmith` would still pass: **the policy must forbid personal data in references** (policy spec). Free-text reasons (`initiation_reason`, `approval_reason`, `cancel_reason`, window `reason`, `revoke_reason`) live in rows readable only by definer code and operators through the overview; the overview does not return them. Retention of these rows is bounded only by the life of the account (cascade on user deletion); the audit table is append-only.

## 7. Risks and limits (stated, not hidden)
1. **Never executed.** Syntax, name resolution, constraint satisfaction by the RPCs' inserts, trigger interplay and every behavior above are unverified; a defect of the kind found in rev3 and rev3.1 is plausible. 2. **Insider collusion** of two distinct, capable, step-up-authenticated operators defeats the control; mitigations are audit, owner notification, the cool-off and owner cancellation. 3. **Different people versus different accounts**: the database cannot tell; the policy must forbid shared accounts and one person holding two accounts. 4. **Quality of the external identity verification** is a procedure; the database records method, references and both operators only. 5. **Owner notification is the application's duty** (email to the address on file and other channels); the database makes the request visible in the owner context. A mailbox compromise defeats the notification. 6. **Unexpected errors after accounting** (deadlock victim, timeout) roll back with their effect (section 5). 7. **Operator removal of factors is manual** and not verified by any function except that a verified factor blocks the window (`factor_removal_required`). 8. **The quotas are counted over `created_at` of durable rows** (24 hours per operator, 7 days per owner); manipulation of the database clock is out of scope. 9. **Staff concurrency, shadow behavior and real Auth integration remain untested** (plan). 10. The `p2:rl:v1:` string in `rl_user_key` is a hash input, not a lock key (the shadow tool namespaces it harmlessly).

## 8. Defect found in rev3.1 while writing rev4 (and what it teaches)
In rev3.1 `rpc_owner_recovery_request` computed `v_cool := clock_timestamp() + 24 hours` and then inserted a row whose `created_at` defaulted to a **later** `clock_timestamp()`. The table's own CHECK `cooloff_until >= created_at + 24 hours` is therefore violated by microseconds and **every owner-code recovery request would fail with a constraint error**. The rolled-back dry execution of rev3.1 could not reveal it (it never called that path with real rows), and neither could static checks or the 293 unit tests. It was found by reading. Rev4 passes `created_at` and `cooloff_until` from one captured instant, and a test asserts the fix. **This is precisely the class of defect the shadow success-path tests exist to find;** rev3.1 should not be applied.
